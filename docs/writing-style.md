[[docs/knowledge-management|知识库管理细则]] 的写作风格。

每篇只讲好一个可独立回答的问题，并在讲清的前提下尽可能简短。写入前先用一句话确定每篇要回答的问题，再将材料分配给对应文档；不能因为同属一个主题、来自同一段讨论，就全部放进一篇。只保留回答本篇问题必需的内容，删去重复和无关展开。整理讨论时，重要问题及结论应各有归属；简短通过拆分实现，不因概念篇篇幅有限而省略其余值得保存的内容。

概念篇讲清「是什么」，必要时简述「为什么需要」。例如「任务状态管理」说明状态包含哪些内容、为什么从上下文中单独维护即可；怎样存储、怎样更新、怎样处理冲突等独立问题分别展开，不继续往概念篇加章节。工具用法、机制、实践和设计文档也各自围绕一个具体问题，不写成主题大全。

先给出核心判断与必要限定，不一次写满。后续追问补充同一问题的条件、因果、例子和来源时更新原篇；追问转向另一个需要展开的问题时另篇记录；只需简短解释或对比的内容仍可留在原篇。追问属于同一大主题，不等于应补进同一篇。

拆分同时看问题是否独立、已有内容量与展开需要，不设固定字数，也不按每段或每个步骤机械拆卡。能用一句话说明的原因或对比、少量引用及简短参考表格，直接附在原篇即可；经过收集整理，有更多材料需要比较、解释或讨论时，再新建卡片。能拟出一个独立标题，不代表当前内容已值得单独成篇。多个步骤共同回答一个问题时保留完整解释链；篇幅明显变长时，先检查是否承载了多个问题，再删减重复与非必要细节，不以换成密集表格或长列表代替拆分。总览只交代定位与组成关系；拆分后，用简短说明引出各篇所回答的问题，并在说明中链接对应卡片，让读者能从入口找到各部分。不复制细则，也不只罗列标题。

正式笔记面向脱离原始对话的阅读：补齐必要的主语、适用场景和术语含义，把「刚才的方案」「上面提到的情况」换成明确对象。只补理解本篇必需的前置说明，已有完整解释时直接链接，不复制整篇背景。

卡片只呈现知识内容，不写新建、整理、拆分、迁移等编辑过程说明，也不附对话来源或卡片沿革。保留有参考、核实或延伸阅读价值的外部资料链接；事实条件、示例与实测的区分仍须保留。不写「本篇拆自……」「按用户要求整理」「此处为整理时补充」等过程交代；需要纠正概念时，直接写准确表述、条件和依据。

用户用例子表达阅读困惑或偏好时，先提取背后的关注点，不把随口举例自动当作文档范围或唯一场景；仅在例子有助于解释且符合保存范围时采用。保存用户的理解时，保留其判断、例子和未解决的疑问；事实有误时就地说明修正及依据，不把个人理解悄悄改成通用解释。Agent 新增的解释、推导和假设案例要与用户表达区分，假设不写成用户经历，未执行的步骤不写成实测结果。

开篇点题：直接给出要回答的核心问题或结论，再展开；不用「先看最小形态」这类不含信息的公式化引导语。概念、总览类文章用一句加粗的核心定义开篇，说明它「是什么（属于哪一类）、有什么特点、边界在哪」——不要只换个说法重复「做什么」；条件、限定和解释用普通文字承接，引用块留给补充说明、示例或需要视觉区分的短段。

不要吝啬分段：当核心定义句本身篇幅较长时，让它单独成段，再接解释；句中的「」强调不必单独成段。

强调用「」，可叠加加粗：句中要突出的关键词、短语用「」包裹，需要更醒目时再加粗，写成 **「关键词」**——网页样式下只用加粗不够显眼，二者同用兼顾语义标记和视觉强度；开篇的核心定义仍保留加粗。列表项冒号前的名称、「边界」这类起分隔作用的引导词，以及本身已独立成段的内容，都不再加「」或加粗。

重要概念在正文首次出现时同时给出中文和英文。标题只有本身是「一个概念」时才中英并写，且「以常用名（主名）在前、另一种语言放括号内」：中文常用写「中文（English）」（如「背压（Backpressure）」「Redis 集群（Cluster）」），缩写、专有名等英文常用写「English（中文）」（如「TLB（快表）」「NDCG@K（归一化折损累计增益）」）。描述性或组合式标题只用中文，纯英文的概念标题则补上中文。

介绍一个新概念时，可按「是什么 → 职责或功能边界 → 与相近概念、产品的区别」展开，再按实际内容裁剪篇幅，不套固定模板。

介绍实现方案的入门用法时，先用简短的原理解释说明它如何工作，再给直观的命令、代码或操作流程，让读者知道启动了什么、任务在哪里执行、关键能力由谁提供，然后说明配置。只需了解「大概怎么用」时，原理、启动示例与关键边界收敛在同一方案卡片；需要独立深入时再拆，不按每个配置项机械拆篇。

非概念类文档（设计、实践、机制、方案、面试等）不要罗列知识点或背答案，多问「为什么需要它、为什么不直接用替代方案、痛点在哪」，再由问题推出做法；可以从最小本质出发（例如 RPC 的本质是一次网络请求），再逐步补齐它比最简形态多出来的部分。段落之间要有因果或转折过渡，让一个问题的结论自然引出下一个问题，不要并列堆砌互不相关的点。

比较方案前，先说明它们的层次与关系：是互相替代、可以组合，还是底层机制与产品封装。存在重叠时，解释采用其中一个会替换什么、保留什么，以及仍需自行完成哪些工作，避免把不同层次的方案写成简单的多选一。

按信息关系突出重点：不同子问题用简短、明确的小节标题定位；并列要点用列表；有共同维度的多个方案、时机或策略优先用表格比较收益、代价与适用条件，不把比较项挤在一段话里。比较后说明取舍或组合方案及其理由，区分「有哪些选择」与「如何选择」。选型文档既要提供可迁移的判断依据，也可补少量具体场景，交代「场景条件 → 建议方案 → 原因 → 何时重新评估」；案例辅助理解，不替代原理与利弊比较，不把有条件的建议写成唯一答案。不为凑结构强制加表格或小节。

短文也要有清晰的阅读重点：核心判断、关键取舍或易错边界用「」标注，必要时叠加加粗；流程用箭头表达。先通过标题、表格和分段建立层次，再少量强调关键句，不靠大面积加粗或缩短成密集段落突出重点。比较表的收益与代价两侧都应突出少量有辨识度的短语，让读者快速识别各方案的特点和主要限制，不能只强调优点。

生命周期、执行流程和数据流转优先用简洁的横向箭头表达，简单链路用一行文字即可；确需图示时优先横向流程图，多组件交互可用时序图，避免占空间的纵向步骤堆叠。生成、保存、刷盘、清理等围绕同一生命周期组织，不机械拆成固定小节；并行或无固定先后的过程用文字注明，不画成必经的串行步骤。

同一主题仅措辞或展示形式不同，复用同一正文；生产实践与面试回答等确有不同问题或使用目的时，才分别保存，并链接共享的基础解释。标题用必要的限定词区分，不复制同源正文，也不固定生成成对版本。

## 阅读验收

保存后按本篇目标读回，检查：

- 能否用一句话说清本文的核心问题；各段是否用于回答它、补充必要参考，或作为入口简短引出细分问题，是否有应另篇展开的细则。
- 在保留必要解释后，是否还有可删的重复、背景或提前展开的细则，能否更简短。
- 不看原始对话，能否知道本文回答什么、结论在什么条件下成立。
- 快速扫读标题、表格与强调句，能否找到核心问题、比较维度和取舍结论，而不必从密集段落中逐项提取。
- 必要的解释是否连续，是否因为删减或拆分而必须反复跳转才能理解核心结论。
- 实践篇能否让读者看懂如何启动与使用；选型篇能否分清方案关系、收益与代价，并根据自身条件作出初步判断，而不只是记住名称或套用案例。
- 链接所在句是否说明为什么需要目标内容，目标章节是否确实提供对应解释；拆分后的总领卡片是否简短引出各部分，能否从入口找到对应内容。
- 用户观点、来源事实、Agent 推导和实测是否可区分，未解决的问题是否仍有标记。

新用语法或调整图表、嵌入、折叠等展示时，核对星云的实际支持并查看渲染效果；尚未验证时明确说明，不以 Obsidian 支持作为星云已支持的依据。普通文字修改读回即可，不要求每次启动 Web。
