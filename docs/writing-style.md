[[docs/knowledge-management|知识库管理细则]] 的写作风格。

每篇保持原子：只回答一个问题，尽可能短，减轻单次阅读负担；独立问题拆成另一篇，不为一篇的完整性堆入多个主题。

开篇点题：直接给出要回答的核心问题或结论，再展开；不用「先看最小形态」这类不含信息的公式化引导语。概念、总览类文章用一句加粗的核心定义开篇，点明主题；条件、限定和解释用普通文字承接，引用块留给补充说明、示例或需要视觉区分的短段。

不要吝啬分段：当加粗句本身是核心结论或核心概念（或篇幅较长）时，让它单独成段，再接解释；普通的加粗强调不必单独成段。

重要概念在正文首次出现时同时给出中文和英文。标题只有本身是**一个概念**时才中英并写（如「背压（Backpressure）」「Redis 集群（Cluster）」），描述性或组合式标题只用中文，纯英文的概念标题则补上中文。

介绍一个新概念时，可按「是什么 → 职责或功能边界 → 与相近概念、产品的区别」展开，再按实际内容裁剪篇幅，不套固定模板。

非概念类文档（设计、实践、机制、方案、面试等）不要罗列知识点或背答案，多问「为什么需要它、为什么不直接用替代方案、痛点在哪」，再由问题推出做法；可以从最小本质出发（例如 RPC 的本质是一次网络请求），再逐步补齐它比最简形态多出来的部分。段落之间要有因果或转折过渡，让一个问题的结论自然引出下一个问题，不要并列堆砌互不相关的点。

并列的功能、要点和对比项用无序列表分行呈现，每项可写成「名称：说明」，避免堆成一段连续文字造成阅读疲劳；列表前后保留必要的引导句或收束句，不把整篇都拆成列表。短文也要突出重点：核心结论、关键链路等用加粗、箭头或简单流程图呈现，不写成没有重点的平铺段落。

同一主题的不同版本（如生产实践与面试回答）拆成独立文档，共用同一基础标题，只在其中一版标题后加「（面试回答）」等备注；各版在开篇用引用块简短引出另一版，例如「面试回答见：[[...]]」，不把同源版本放到文末当“推荐阅读”。
