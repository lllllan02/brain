[[docs/knowledge-management|知识库管理细则]] 的写作风格。

每篇只讲好一个可独立回答的问题，并在讲清的前提下尽可能简短。写入前先用一句话确定每篇要回答的问题，再将材料分配给对应文档；不能因为同属一个主题、来自同一段讨论，就全部放进一篇。只保留回答本篇问题必需的内容，删去重复和无关展开。整理讨论时，重要问题及结论应各有归属；简短优先通过聚焦、去重与链接已有展开实现，确有独立问题再拆分，不因概念篇篇幅有限而省略其余值得保存的内容。

概念篇与总览应让读者知道「是什么、为什么需要、基本怎样运作、边界在哪里」，按对象和本篇问题取舍深度；这些是内容检查角度，不是固定章节标题。压缩时按本篇的解释关系组织段落、列表或示例，不把某次采用的「一句定义加若干要点」推广为通用模板；也不为形式不同而刻意变换结构。为什么需要应落到具体痛点，说明原有做法遇到什么困难、该概念通过什么方式缓解，不能只写“提高效率”等笼统收益。例如「任务状态管理」说明状态包含哪些内容、为什么从上下文中单独维护即可；怎样存储、怎样更新、怎样处理冲突等独立问题分别展开，不继续往概念篇加章节。工具用法、机制、实践和设计文档也各自围绕一个具体问题，不写成主题大全。

先给出核心判断与必要限定，不一次写满。后续追问补充同一问题的条件、因果、例子和来源时更新原篇；追问转向另一个需要展开的问题时另篇记录；只需简短解释或对比的内容仍可留在原篇。追问属于同一大主题，不等于应补进同一篇。

逐层探索中的专题及子专题都先保持简短，尤其是从面试题切入的梳理：一句话能准确讲清的直接写；需要更多解释的先列关键词、问题清单或简短表格，供后续选择展开，不默认写成详细教程或完整答案。清单保留当前层的范围和必要边界，不把尚未展开的内容压成密集答案，也不提前批量创建子文。分层不是无限递归：当一篇已围绕明确问题给出清楚的知识点，且用户确认当前深度足够时，就收束为叶子卡片，保留结论与必要边界，去掉预设的追问列；不要求每行继续拆篇，也不把每篇都写成下一层目录。用户明确按表格中的独立问题拆篇时，入口保留简短介绍，各问题以简洁正文形成叶子卡片；叶子表示不再预设下层分支，不表示只能保留一句表格结论。学习一项新技术时，可以按理解需要增加解释、例子与实现细节，但仍先整体、后分支、再局部机制，每次只深入当前选定的一层；“学习新技术”不意味着一次写尽全部细节。展开与收尾按 [[docs/knowledge-management#大专题的分层推进|分层推进]] 执行；用户明确要求一次完整论述时再按其要求调整。

拆分同时看问题是否独立、已有内容量与展开需要，不设固定字数，也不按每段或每个步骤机械拆卡。拆分前先写出核心解释：若一句话已经讲清原因与必要条件，就留在原篇，不另建卡片，也不为支撑独立成篇而追加算例、重复推导或旁支。少量引用及简短参考表格同样可留在原篇；只有当前问题确实需要独立展开，才新建卡片。能拟出一个独立标题，不代表当前内容已值得单独成篇。多个步骤共同回答一个问题时保留完整解释链；篇幅明显变长时，先检查是否承载了多个问题，再删减重复与非必要细节，不以换成密集表格或长列表代替拆分。专题入口先用少量连贯段落保留定义、痛点、基本机制与必要边界，让读者不跳转也能理解主题；内容较多时按实际问题分节，在对应解释中引出子文，详细示例、操作步骤与独立问题放入子文。重要分支仍须完整可见，不为每篇子文机械增加介绍段，也不把子文摘要依次堆回入口。

正式笔记面向脱离原始对话的阅读：补齐必要的主语、适用场景和术语含义，把「刚才的方案」「上面提到的情况」换成明确对象。只补理解本篇必需的前置说明，已有完整解释时直接链接，不复制整篇背景。

知识卡片和专题入口的内部链接应穿插在正文中，在解释概念、机制、证据或取舍时就地引出对应文档。不在文末或其他位置单列「参考文档」「相关内容」「延伸阅读」或「接下来读什么」等内部链接清单，也不把清单换成一段逐篇推荐的文字。每个链接所在句应提供有用解释，不为放链接添加过场；readings 的原文出处用 `source` 元数据记录；inbox、notes 不设置来源元数据，也不写成外部摘要的再摘要，而是围绕自己的问题提炼认识，必要的参考随正文引出。用户明确请求的学习计划可在对话或相应计划文档中表达，不自动套入知识正文。

卡片只呈现知识内容，不写新建、整理、拆分、迁移等编辑过程说明，也不附对话来源或卡片沿革。保留有参考、核实或延伸阅读价值的外部资料链接；事实条件、示例与实测的区分仍须保留。不写「本篇拆自……」「按用户要求整理」「此处为整理时补充」等过程交代；需要纠正概念时，直接写准确表述、条件和依据。

用户用例子表达阅读困惑或偏好时，先提取背后的关注点，不把随口举例自动当作文档范围或唯一场景；仅在例子有助于解释且符合保存范围时采用。保存用户的理解时，保留其判断、例子和未解决的疑问；事实有误时就地说明修正及依据，不把个人理解悄悄改成通用解释。Agent 新增的解释、推导和假设案例要与用户表达区分，假设不写成用户经历，未执行的步骤不写成实测结果。

开篇先给结论：用一句或一个短段直接回答本篇问题，带出关键特性及其原因或价值，再逐项解释依据、差异、例子和必要边界。比较篇先说「关键差异 → 带来的收益 → 为什么契合当前需求」，不能只说“存在差异”或把答案留到表格和末尾；其他文档也沿用先结论后展开的顺序，按问题选择需要交代的“是什么、为什么”，不机械凑齐栏目。不用「先看最小形态」这类不含信息的公式化引导语。定义对象须对应当前实际讨论：术语在语境中指代规则、机制或用法时，应直接解释它，不停留在字面组成或词义拆解。概念介绍先给出清晰的「什么是什么」定义：指出对象所属的类别（如数据结构、操作、机制、属性或关系），再给出区别于同类的关键特征；随后解释为什么需要、做什么及怎样运作。不能用「X 是为了……」或仅列动作、用途代替定义，也不能把所有对象笼统归为机制。核心定义可加粗，原因与用途可以用短句承接，不机械设置固定小节或为凑全栏目扩写。条件、限定和解释用普通文字承接，引用块留给需要视觉区分的补充。

每个核心概念的定义单独成段，不以句子长短为条件。同篇介绍多个概念时，分别呈现定义，再展开解释或比较，不把多个定义合并成一段或一整块加粗。精简通过删去重复内容实现，不通过减少必要分段实现；句中的「」强调不必单独成段。

强调用「」，可叠加加粗：句中要突出的关键词、短语用「」包裹，需要更醒目时再加粗，写成 **「关键词」**——网页样式下只用加粗不够显眼，二者同用兼顾语义标记和视觉强度；开篇的核心定义仍保留加粗。列表项冒号前的名称、「边界」这类起分隔作用的引导词，以及本身已独立成段的内容，都不再加「」或加粗。

概念介绍的标题直接使用简短的概念名，不把引出概念的疑问写成标题。为什么需要它、它与当前问题有什么关系，放在引用处用通俗说明或问题引出；目标文档以定义开篇，再按需解释原因、做法与边界。只有内容确实复杂、需要独立展开的问题，才另设问题型文章，不将概念介绍包装成长问句。

重要概念在正文首次出现时同时给出中文和英文。标题只有本身是「一个概念」时才中英并写，且「以常用名（主名）在前、另一种语言放括号内」：中文常用写「中文（English）」（如「背压（Backpressure）」「Redis 集群（Cluster）」），缩写、专有名等英文常用写「English（中文）」（如「TLB（快表）」「NDCG@K（归一化折损累计增益）」）。描述性或组合式标题只用中文，纯英文的概念标题则补上中文。

正文与摘要都应提炼核心结论及其解释关系，不能只留下术语、目录或“本文介绍了什么”。概念介绍可顺着「是什么 → 原有痛点 → 解决方式 → 边界」展开，实践篇则保留完成操作所需的步骤；不要求每篇都补全无关背景或实现细节。

介绍实现方案的入门用法时，先用简短的原理解释说明它如何工作，再给直观的命令、代码或操作流程，让读者知道启动了什么、任务在哪里执行、关键能力由谁提供，然后说明配置。只需了解「大概怎么用」时，原理、启动示例与关键边界收敛在同一方案卡片；需要独立深入时再拆，不按每个配置项机械拆篇。

解释设计特征时，先说明为什么需要这种特征、它降低了什么成本或解决了什么困难，再简述怎样做到及可观察的现象；不能只解释形成原因而遗漏设计目的。介绍维护或调整机制时，还应简要交代它是什么、实际改变了哪些对象、何时需要以及付出的代价；不能把“为什么触发”当作整篇重点而省略变化与成本。围绕某个系统选型的比较，应把差异落回该系统的需求与选择理由，而不止并排列出特点。

非概念类文档（设计、实践、机制、方案、面试等）不要罗列知识点或背答案，多问「为什么需要它、为什么不直接用替代方案、痛点在哪」，再由问题推出做法；可以从最小本质出发（例如 RPC 的本质是一次网络请求），再逐步补齐它比最简形态多出来的部分。段落之间要有因果或转折过渡，让一个问题的结论自然引出下一个问题，不要并列堆砌互不相关的点。

比较方案前，先说明它们的层次与关系：是互相替代、可以组合，还是底层机制与产品封装。存在重叠时，解释采用其中一个会替换什么、保留什么，以及仍需自行完成哪些工作，避免把不同层次的方案写成简单的多选一。

讨论机制或设计时，先明确处理对象，再把抽象落到可判断的输入、执行者、规则与结果，并用一个小例子说明边界；例如「交给规则判断」仍需说明规则依据什么、返回什么。跨工具的统一设计应说明共享判断与各工具适配的分工，不能只给每个函数换一个检查方法名。是否展开实现，以用户当前学习深度为准。涉及模型与程序协作时，区分模型判断或生成的内容，与程序负责的选择、校验、存储和组装；不要用一个含糊的动作替代双方职责。涉及存储与读取时，交代保存对象、位置、格式及读取后的用途；具体字段用 JSON／JSONL 或最小伪代码说明，不为展示格式扩展成完整工程。

实现示例优先使用用户熟悉的 Go 或 Go 风格伪代码，以最少代码体现关键调用链、输入输出与判断点，不能只用抽象描述代替用户要看的实现。已有成熟 SDK 时优先使用，省去与本篇目标无关的 HTTP 封装、序列化样板和基础设施；只有协议格式或底层通信本身就是讨论对象时才展开这些细节。原文 SDK 示例可保留其语言并标明来源，不为统一语言臆造不存在的 Go 接口；注明依赖、版本、运行条件，以及可运行代码或伪代码和实际验证状态。用户暂不需要实现细节时不主动展开完整工程。

同一组实践尽量沿用一个业务例子。已有基础实现时，后续方案链接它，只展示真正变化的调用或配置；先判断差异是否值得独立成篇。若只是把已有 Client 接进已有模型循环，简短衔接说明即可，不因能组合运行就维护第三套示例。消息格式示例与 SDK 实现回答不同问题，可以分别保留，但不互相复制整段代码。

按信息关系突出重点：不同子问题用简短、明确的小节标题定位；并列要点用列表；有共同维度的多个方案、时机或策略优先用表格比较收益、代价与适用条件，不把比较项挤在一段话里。比较后说明取舍或组合方案及其理由，区分「有哪些选择」与「如何选择」。选型文档既要提供可迁移的判断依据，也可补少量具体场景，交代「场景条件 → 建议方案 → 原因 → 何时重新评估」；案例辅助理解，不替代原理与利弊比较，不把有条件的建议写成唯一答案。不为凑结构强制加表格或小节。

短文也要有清晰的阅读重点：核心判断、关键取舍或易错边界用「」标注，必要时叠加加粗；流程用箭头表达。先通过标题、表格和分段建立层次，再少量强调关键句，不靠大面积加粗或缩短成密集段落突出重点。比较表的收益与代价两侧都应突出少量有辨识度的短语，让读者快速识别各方案的特点和主要限制，不能只强调优点。

流程篇以讲清完整链路为目标：谁在什么条件下发起、谁执行、输入输出如何传递、怎样继续或结束。优先用同一个小场景串起各步，保留理解流程所需的检查与边界；较长的报文示例、实现代码或独立异常问题另行展开，已有文档能承接时直接复用，不为少量提示机械新建卡片。下方只保留直接相关的示例或实现入口，不补成周边能力目录。

生命周期、执行流程和数据流转优先用简洁的横向箭头表达，简单链路用一行文字即可；确需图示时优先横向流程图，多组件交互可用时序图，避免占空间的纵向步骤堆叠。生成、保存、刷盘、清理等围绕同一生命周期组织，不机械拆成固定小节；并行或无固定先后的过程用文字注明，不画成必经的串行步骤。

面试准备可以决定讨论的切入点，但保存为知识笔记时，标题以主题或具体问题命名，正文围绕概念、机制、适用条件与边界展开，不因讨论用于面试就冠以「面试准备」或限定为答题要点。用户明确要求题库、模拟面试或面试记录时，再采用对应形式。

同一主题仅措辞或展示形式不同，复用同一正文；生产实践与面试回答等确有不同问题或使用目的时，才分别保存，并链接共享的基础解释。标题用必要的限定词区分，不复制同源正文，也不固定生成成对版本。

## 图文分工

用户要求配图时，交付须包含实际可见且经过目视检查的图，失效链接或未能预览的图源不能算完成。外部图无法可靠展示时，在获准自行绘图的范围内生成本地图片并嵌入对应正文，保留可编辑源文件和依据。

知识配图优先按具体内容设计画面，不默认套用时序图或流程框。用户偏好让实际对象、标签、位置、分组和状态变化承担解释：例如调度可画一批带约束的调用如何分到并发执行与等待区域，并直接标明等待原因；不要把所有场景都画成同一种箭头链。清晰主线应由核心对象的流转与变化形成，各环节仍需展示内部组成、比对或分配；不能为减少分支退回「步骤方框＋说明文字」。先确定需要凸显的关系，再选择画面，确有必要时才使用标准图表。

默认采用用户已认可的[权限与审批图](../content/assets/tool-permissions.png)这类对象与机制表达：以一个核心对象贯穿横向主线，画出规则记录、请求、审批单、执行对象等实际组成，以及字段如何被取出、比对、绑定和改变状态；次要分支就近用较轻的对照或分区呈现，不与主线争夺注意力。需要例子时明确标为假设，让例子解释机制，不把具体业务固化为通用模板。

视觉上采用白底、留白、清晰中文和少量语义色；同一对象的标识与颜色保持一致，容器形态、内部标签和局部布局表达对象职责，连线只连接必要流转。验收时检查读者能否看见「拿什么与什么比较、产生了什么记录、哪个对象因此获准进入下一环节」，不能仅以步骤齐全、连线少或排列整齐判断直观。

连线优先使用水平或垂直直线，必要时只转一次直角。出现「横—竖—横」或多次折返时，先调整节点位置与连接端口，避免靠绕线迁就布局；验收时逐条检查折点和落点，同时保留原有关系与返回位置。绘制前核对本图已明确要覆盖的对象和分支，简化优先调整布局与视觉层级，不删去必要节点；有循环时标清回到哪一步。

配图辅助解释文字不容易讲清的关系、变化或边界，放在对应位置，不默认做整篇总结图。专题入口需要串联多个分支时，可用一张整体关系图展示各部分如何配合；子文的图聚焦各自机制，不在总图中复制全部细节。图已清楚表达的过程，正文不再逐框复述，只补原因、条件与局限。

图应展示具体对象及其变化：筛选画出「多个中取出少量」，摘要画出「原始消息变成摘要与保留消息」，按需读取画出「大文件中取出一个片段」，更新画出「新信息怎样改变旧状态」。这些是表达方法，不是所有图必须包含的组件。记录格式可直接用 JSON／JSONL，简单映射可用表格；不能只把术语装进方框当作机制图，也不为配图引入正文未讨论的分支或组件。

同一组对比保持一致的时间或流向；确有先后交互时可借鉴时序图，用状态快照补充普通箭头难以表达的变化。多行多列各有含义时，用简短标签说明行的职责与列的阶段；处理后的结果已清楚展示，就不在下一列原样复制。关键阈值、分界、保留与变化要有明确标记，颜色和对象标识前后一致。修改图片保留原有解释作用，导出后实际查看，检查内容含义、方向、落点与可读性。

## 精简与依据

精简先删口头过渡、重复结论、图文复述及超出当前层的问题。来源卡已展开的参数和实现，入口只留支持理解的结论与就地链接；已有概念入口能承接多个案例时，不额外创建仅汇集链接的「不同方案做法」入口。简洁不等于撤掉必要依据或把有效内容压成无法独立理解的术语。

技术机制文章动笔前，先完成问题与依据的核对，不能先凭熟悉的结论写完，再找链接佐证：

1. 还原原有过程：用一个具体输入说明，不采用该机制时，谁拿到什么数据、按什么规则处理、在哪里出现额外成本或能力限制。主动追问「既然已有这些信息，为什么不直接完成」，不能等用户指出解释缺口。
2. 带着缺口检索：先读库内候选，再核对官方文档、实现或研究中有关原流程、约束与新机制的说明。关键原因跨越多个机制时，继续核对相邻机制，不能只读目标功能的介绍页。事实及版本条件要有依据；资料未解释的原因保留为未知或明确标为推导，不臆测设计动机。不以来源数量作为充分标准：能支持本篇关键因果与边界才停止，必要时用最小实验验证行为。
3. 推演后再写：保持同一输入，对比引入机制前后的处理，指出改变和保留的步骤。例子应暴露导致问题的结构或约束，让读者看见问题如何产生，再看见机制如何处理；官方例子也需判断是否适合本篇学习路径。推演无法说清时先补检索，不用更多术语或更长正文掩盖。

核对用临时的问题、依据与推演即可，不新增流程报告，也不把检索过程塞进正文。区分数据结构的限制、执行分工和实现选择，不将它们串成未经支持的必然因果。例如 ICP 需要同时核对范围如何构造、剩余条件原本在哪一层判断；匹配记录分散不能单独推出「必须由 Server 层判断」。范围例子服务于这篇解释，不固定为所有机制文章的模板。

从参考形成建议时，先读懂官方说明、源码或实验的实际做法，再归纳可借鉴的规则。产品事实、跨来源归纳和自拟方案分别表述；没有依据的方案不包装为通用机制，也不为凑章节扩写。不同实现只有在统计对象、单位、分母与条件可比时才合并比较；阈值要说明什么量达到什么比例，处理后的大小与触发阈值分别表达，未知参数明确未知；示例数字不能当默认值或推荐标准。

## 阅读验收

保存后按本篇目标读回，检查：

- 能否用一句话说清本文的核心问题；各段是否用于回答它、补充必要参考，或作为入口简短引出细分问题。独立子文是否确有展开必要；若一句解释已足够，其余只是重复或附带延伸，应合回原篇；确有独立细则才拆分。
- 在保留必要解释后，是否还有可删的重复、口头过渡、图文复述或提前展开的细则；已有入口和子文能否承接，是否新增了同义入口。
- 不看原始对话，开头能否直接回答本篇问题，并说明结论的必要条件；概念定义能否明确回答「它是哪类东西，有什么关键特征」，而非只回答用途；比较篇能否从关键差异看出对当前需求的收益或代价，而非只说“更适合”或把答案留在表格末尾。
- 快速扫读标题、表格与强调句，能否找到核心问题、比较维度和取舍结论，而不必从密集段落中逐项提取。同一问题有多个解决办法时，是否在原因之后集中呈现方案、所解决的开销与主要边界，再展开必要细节；不能把并列方案散落在长例子或不同问题之间，使读者只记住最先出现的一种。可按内容选短列表或对照表，不强制所有文章使用同一版式。
- 必要的解释是否连续：假设读者只掌握正文已交代或明确引用的前置知识，能否从例子判断「原过程在哪里遇到问题、为什么、该机制具体改变哪一步、什么仍未解决」，而不只是复述动作顺序。对关键的“因为……所以……”逐项核对依据，区分结构限制与执行选择；涉及优化时，用同一输入核对有无优化的差异，以及原路径为何没有提前完成该工作。只列功能收益、附有官方链接或例子能够运行，都不能代替这一检查。检查是否因删减或拆分而必须反复跳转才能理解主题；专题入口顶部是否已有完整的核心介绍，而非仅剩一句定义。
- Reading 是否按 [[docs/knowledge-management#来源与巡检|来源规则]] 保留原文的重要内容与论证过程；是否把入口的简洁要求误用于来源总结，或用结论、术语清单和原文定位替代机制、证据与取舍。
- 概念卡片脱离原话题后是否仍成立：应用章节、例子和链接是否用于解释概念自身，还是只因本次讨论提到而加入；后者按 [[docs/metadata-and-links#术语库|术语库边界]] 归回使用处。允许必要的简短释义，不在多篇中重复完整定义与通用例子。
- 流程篇能否顺着主线看清参与者、数据与控制的流转，是否被较长示例或异常分支打断。实践篇能否看懂如何启动与使用，代码是否聚焦关键差异、是否重复已有实现或包含无关封装；选型篇能否分清方案关系、收益与代价，并根据自身条件作出初步判断，而不只是记住名称或套用案例。
- 链接名称、分组或所在句是否能说明目标内容，目标章节是否确实提供对应解释；入口能否快速找到各分支，是否存在删去也不损失信息的链接介绍段，普通子文是否重复了上级的整组导航，是否另列内部参考或后续阅读清单，而未把链接融入对应解释。
- 简化或拆分后，重要问题是否仍清楚可见且有归属；按 [[docs/knowledge-management#专题入口与阅读组织|专题入口细则]] 对照覆盖，不能仅以篇幅缩短或链接有效判定完成。
- 用户观点、来源事实、Agent 推导和实测是否可区分，未解决的问题是否仍有标记。

新用语法或调整图表、嵌入、折叠等展示时，核对视界的实际支持并查看渲染效果；尚未验证时明确说明，不以 Obsidian 支持作为视界已支持的依据。普通文字修改读回即可，不要求每次启动 Web。
