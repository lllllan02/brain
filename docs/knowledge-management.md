[[AGENTS|AGENTS.md]] 的操作细则。按当前任务读取对应部分；文档格式与链接规范见 [[docs/metadata-and-links|文件名、元数据与链接]]，写作风格见 [[docs/writing-style|正文写法]]。本篇内容继续增长时，按主题拆分到独立文档，保持每篇简短。

## 会话定向

首次进入项目读 README，规则已读且未变化时不重复读取。先确认本次任务是查询、保存还是整理，明确要回答或记录的问题。用 `git log --oneline -10` 与 `git status --short` 回顾近期改动和工作区状态，判断是否有未提交内容、最近改过哪些文档，避免重复保存、覆盖他人编辑或与未提交改动冲突。用户指定文件或本轮对话已有相关文档时先读这些候选，不从头搜索。

## 检索与候选阅读

先用程序搜索得到候选路径和命中片段，再由 Agent 阅读正文判断。优先用项目只读检索层 `node scripts/retrieve.mjs query <词...>`（或 `make search q="..."`）：它复用星云的解析逻辑，覆盖 `content/notes/` 与 `content/inbox/`，返回候选、命中字段与片段，省去逐篇读取和手工解析元数据。检索层不可用或需要精确到行时，回退 Agent 自带的检索工具（基于 ripgrep）或 shell 的 `rg`、`grep -R -n`。搜索只扫描文件，无需把每篇正文交给模型；一次组合主题词、简称、同义词，复用同轮结果完成内容定位、查重与关系维护。

1. 用户指定文件或当前对话已有相关文档时，先读这些候选。首次进入项目读 README，规则已读且未变化时不重复读取。明确任务是查询、保存还是整理，普通查询不写文件。
2. 未确定候选时，批量检索文件名和 `content/notes/`、`content/inbox/` 的属性、正文，查询结果区分正式笔记与待处理内容。用能区分问题的词，避免只搜「原理」「性能」等宽泛词；不按单一 category 限死范围。
3. 优先查看标题或别名直接匹配、正文回答同一问题的候选，其次看命中章节，再考虑只在标签或引用中提及的文档。命中次数和目录顺序不代表相关度。
4. 先读候选的元数据、核心回答与命中章节；短文可整篇读，长文按行号读取完整相关段落，写入前再核对全文结构与会影响结论的条件。别名可能采用 YAML 多行列表，不能仅靠匹配 `aliases:` 所在行判断是否存在。
5. 找到支持回答或足以确定写入位置的正文后停止扩大搜索。需要前置解释、冲突依据或影响范围时再沿链接阅读，不递归遍历整张关系图。
6. 候选不足时，补充上位概念、替代措辞，或在候选中取消命中数限制。正式笔记与 inbox 均无合适内容时，按任务需要扩大到已存在的 sources；原文只作来源依据，不直接作为整理笔记覆盖。缺少来源依据时保留待核实说明，不自行补造结论。

以下命令在项目根目录执行，词语和路径按任务替换；文件名检索与内容检索可在同一轮执行：

```sh
# Agent 检索层（推荐，覆盖 notes 与 inbox，返回候选、命中字段与片段）
node scripts/retrieve.mjs query 覆盖索引 回表

# 查名称；保留结果供后续定位和文件名查重（rg 可用时）
rg --files content -g '*.md' | rg -i 'mysql|index|explain'
# 无 rg 时用 find + grep
find content -name '*.md' | grep -iE 'mysql|index|explain'

# 一次搜索正式笔记与待处理内容，返回每个文件最多 3 条命中（rg 可用时）
rg -n -i -F -m 3 -e '覆盖索引' -e '回表' -e 'covering index' content/notes content/inbox -g '*.md'
# 无 rg 时用 grep -R
grep -R -n -i -m 3 -E '覆盖索引|回表|covering index' content/notes content/inbox --include='*.md'

# 已定位候选后，按其实际路径读取正文；长文按实际行号取章节
sed -n '1,100p' content/inbox/mysql-explain-extra.md
```

`-m 3` 是首轮控制输出的示例，不是候选总数或完整性保证。命中太多时先只取路径，或增加有区分度的词；不要用 `head` 截掉候选后就判断已查全。发现工具输出截断，应缩小单批范围或分批读取。无匹配（`rg` 退出码 1、`grep` 退出码 1）是正常结果；其他非零退出码是执行错误，需处理，不能当作无内容；不存在的可选目录无需搜索。

## 归属判断与写回

读过候选后，按它回答的问题决定写入位置；一次输入含多个独立问题时分别判断，不为每段话各建一篇。

| 新内容与已有正文的关系 | 操作 |
| --- | --- |
| 回答同一问题，补充条件、解释、证据或修正 | 更新原文对应位置，保留有效内容与出处 |
| 为原问题服务的附属细节 | 补充现有章节，必要时增加小节 |
| 回答可独立成立的问题，候选仅顺带提及 | 新建笔记，在有意义的提及处连接已有正文 |
| 已有正文完整覆盖，没有新增依据或修正 | 不重复写入，向用户指出已有位置 |
| 与旧结论冲突 | 核对适用条件及双方依据，标明争议或过时，不静默覆盖 |
| 用户要求保存，但内容尚未成形或无法确定归属 | 暂存 inbox，说明待整理或待核实事项 |

新建前，若首轮只查了文件名或属性，补一次正式笔记与 inbox 待处理内容正文的主题词与同义词检索；已经覆盖的检索不重复执行。已有相似候选须读正文后再决定。检索不足或索引故障时不能据此宣称「库内不存在」，应使用文件检索兜底。沿用 `content/` 文件列表核对拟用文件名，遵守 [[docs/metadata-and-links#文件名与属性|文件名与属性]] 的命名规则。

写回前重新核对目标当前内容和工作区已有改动；若其他编辑改变了候选，重新判断合并位置，避免用旧正文覆盖。新建、更新的目录与属性按 [[docs/metadata-and-links|格式与链接规范]] 处理。查询结果引用实际文档，区分库内依据与额外补充。

保存后复用候选和已知引用，仅补搜新概念、被修正的结论及目标链接，维护实质受影响的正文。读回差异，检查是否保留原意与出处、是否重复、日期和属性是否合理、新增或变更链接的目标与锚点是否存在；移动、合并或重命名还需维护全部入站引用与附件路径。仅格式或属性调整不刷新 updated_at。完成后简短报告实际文件、修改理由、关系维护与待核实事项，不生成额外操作报告，不自动提交或发布。

## 修改操作

同一问题更新原文，附属细节补章节，只有独立问题才新建。以下是原文已存在、需要改变结构或位置时的操作；每种操作都先查全部入站引用（`node scripts/retrieve.mjs links <文件名>` 一次列出出链、入链与断链），完成后维护受影响的链接与附件路径，并读回检查。

- **合并**：两篇回答同一问题时，选内容更完整的一篇为主，吸收另一篇的有效正文与出处；把指向被合并文档的双链按引用意图改指向主文档并保留显示名，确认无残留后删除或移入 trash。
- **拆分**：一篇同时回答多个独立问题时，按原子原则拆成多篇，各篇只留自己的问题与依据；把原双链按语义改指向对应新文档，不留断链。
- **重命名**：默认不改名。确需改名时先记录旧名到新名及全部入站引用，改名后逐一更新并检查残留、断链与歧义。
- **归档**：内容当前先精简掉但可能恢复时移入 `content/trash/`；不再恢复时按 [[docs/metadata-and-links#链接与合并|链接规则]] 把入站双链降级为普通文字，保留原句语义。

以上操作保留有效内容与出处、保留原文创建日期、维护附件路径；合并与拆分后检查原链接是否仍指向同一内容，而非只判断目标是否存在。

## 冲突与结论维护

区分事实、个人理解、推导与实测，保留关键来源与适用条件。新信息与旧结论冲突时，先核对双方的适用条件、时间与依据，不因来源较新就自动覆盖。需要保留争议时，在原结论处用统一标注记录，便于检索与复核：

```markdown
> **争议**：新结论……；旧结论在其适用条件（……）下仍成立。依据：……。
```

被新来源取代的旧结论用 `> **过时**：……（由 [[新文档]] 取代）` 标注，保留结论与出处，不静默删除历史。跨文档的冲突在双方各自标注并互相链接。未执行或未核实的结论注明「待核实」，不写成既定事实。

## 查询与答案归档

查询时始终先检索再回答，引用实际文档并给出文件名，明确区分「库内结论」与「额外补充」；库内没有依据时说明检索范围与结果，不用记忆冒充库内内容。普通查询不写文件。

答案是对比、综合或可复用的新结论时，Agent 可主动提议保存；用户要求保存时，按普通笔记规则新建正式笔记，链接被引用的库内文档，不把答案并入被引用的原文，也不为每个问题都建一篇。星云提供随机复习，暂不记录掌握程度或安排间隔复习。

## 索引的现状与维护边界

`scripts/retrieve.mjs` 是供 Agent 使用的只读检索层，复用 [[apps/web/README|文档阅读页面]] 的解析逻辑（frontmatter、双链、锚点、反链），覆盖 `content/notes/` 与 `content/inbox/`，每次按当前源文件实时生成、不落地缓存，因此不会与正文不一致。子命令：`index` 输出每篇一行的 JSON（不含正文），`query` 返回紧凑候选，`links` 查出入链与断链，`lint` 做结构巡检；它依赖 `apps/web` 的依赖，首次使用前执行 `make install`。

正文仍是唯一内容来源，检索层是可重建的派生视图，不另建人工维护的导航正文，也不进入公开发布范围。读取候选和写回始终以当前源文件为准，不能仅凭检索层零命中决定新建；规模明显增大后，再考虑落地持久索引或全文引擎。

## 来源与巡检

自己的内部文档直接迁入 notes，不生成重复原文、数据库快照或迁移备份。外部资料通常只引用链接；用户提供需要保留的原文件或明确要求保存原文时，才建立 `content/sources/`，记录出处、保存时间和版本。图片等附件按需存入 assets。

原文值得保留的情况：页面可能删除或改写；需要固定引用当时的措辞或数据；本地批注、PDF、付费或离线材料无法仅靠链接复现。Agent 可以提出保存理由，普通引用不自动下载整份原文；保存后与整理笔记区分，不再覆盖为总结稿。

冲突结论说明双方依据与条件，不因来源较新就自动覆盖旧结论。实践卡保留环境、步骤和结果，个人想法不强制改写为知识卡。

用户要求巡检时，按下列清单检查；可确定的链接与格式错误直接修复，事实争议先报告：

- **断链与歧义**：双链目标或锚点不存在，或多篇同名导致无法唯一解析。
- **重复**：多篇回答同一问题，或正文高度重叠。
- **孤立**：没有任何入站双链，也未被 README 等入口文档提及。
- **元数据**：title、category、tags、type 与日期是否合理，日期是否与正文最后实质变更一致。
- **过时与冲突**：结论已被取代却未标注，或存在无依据的过期内容。
- **格式与写作**：是否违反 [[docs/metadata-and-links|格式规则]] 与 [[docs/writing-style|写作规则]]。

链接与元数据的结构性核对可用 `node scripts/retrieve.mjs lint`（或 `make lint`）批量执行，它检查断链与歧义、重复文件名、缺少 frontmatter 与 title、日期、命名、链接写法与孤立文档。巡检只报告结构问题，事实争议由 Agent 判断，不代替人做事实判断。内容默认私人，公开发布须明确授权具体文件；授权文件清单的过滤先于搜索、关系与附件生成，不依赖文档里的可见性字段。
