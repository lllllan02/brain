[[AGENTS|AGENTS.md]] 的操作细则。按当前任务读取对应部分；文档格式与链接规范见 [[docs/metadata-and-links|文件名、元数据与链接]]，写作与阅读验收见 [[docs/writing-style|正文写法]]。

用户通过星云或 Obsidian 学习，Agent 负责把获准保存的资料、讨论和反馈整理成可独立阅读的笔记。基本流程是「明确问题 → 检索已有正文 → 判断归属 → 写回与关联修订 → 验收 → 按阅读反馈继续改进」。规则以本项目文档为准；项目 Skill 如需封装，只编排步骤并引用这些规则，不另存一套约束正文。

## 会话定向

首次进入项目读 README，规则已读且未变化时不重复读取。先确认本次任务是查询、保存还是整理，明确要回答或记录的问题。用 `git log --oneline -10` 与 `git status --short` 回顾近期改动和工作区状态，判断是否有未提交内容、最近改过哪些文档，避免重复保存、覆盖他人编辑或与未提交改动冲突。用户指定文件或本轮对话已有相关文档时先读这些候选，不从头搜索。

## 检索与候选阅读

先用程序搜索得到候选路径和命中片段，再由 Agent 阅读正文判断。优先用项目只读检索层 `node scripts/retrieve.mjs query <词...>`（或 `make search q="..."`）：它复用星云的解析逻辑，覆盖 `content/notes/` 与 `content/inbox/`，返回候选、命中字段与片段，省去逐篇读取和手工解析元数据。检索层不可用或需要精确到行时，回退 Agent 自带的检索工具（基于 ripgrep）或 shell 的 `rg`、`grep -R -n`。搜索只扫描文件，无需把每篇正文交给模型；一次组合主题词、简称、同义词，复用同轮结果完成内容定位、查重与关系维护。

1. 用户指定文件或当前对话已有相关文档时先读这些候选；普通查询不写文件。
2. 未确定候选时，批量检索文件名和 `content/notes/`、`content/inbox/` 的属性、正文，查询结果区分正式笔记与待处理内容。用能区分问题的词，避免只搜「原理」「性能」等宽泛词；不按单一 category 限死范围。
3. 优先查看标题或别名直接匹配、正文回答同一问题的候选，其次看命中章节，再考虑只在标签或引用中提及的文档。命中次数和目录顺序不代表相关度。
4. 先读候选的元数据、核心回答与命中章节；短文可整篇读，长文按行号读取完整相关段落，写入前再核对全文结构与会影响结论的条件。别名可能采用 YAML 多行列表，不能仅靠匹配 `aliases:` 所在行判断是否存在。
5. 找到支持回答或足以确定写入位置的正文后停止扩大搜索。需要前置解释、冲突依据或影响范围时再沿链接阅读，不递归遍历整张关系图。
6. 候选不足时，补充上位概念、替代措辞，或在候选中取消命中数限制。正式笔记与 inbox 均无合适内容时，按任务需要扩大到已存在的 sources；原文只作来源依据，不直接作为整理笔记覆盖。缺少来源依据时保留待核实说明，不自行补造结论。

以下命令在项目根目录执行，词语和路径按任务替换；文件名检索与内容检索可在同一轮执行：

```sh
# Agent 检索层（推荐，覆盖 notes 与 inbox，返回候选、命中字段与片段）
node scripts/retrieve.mjs query 覆盖索引 回表

# 查名称；保留结果供后续定位和文件名查重（rg 可用时）
rg --files content -g '*.md' | rg -i 'mysql|index|explain'
# 无 rg 时用 find + grep
find content -name '*.md' | grep -iE 'mysql|index|explain'

# 一次搜索正式笔记与待处理内容，返回每个文件最多 3 条命中（rg 可用时）
rg -n -i -F -m 3 -e '覆盖索引' -e '回表' -e 'covering index' content/notes content/inbox -g '*.md'
# 无 rg 时用 grep -R
grep -R -n -i -m 3 -E '覆盖索引|回表|covering index' content/notes content/inbox --include='*.md'

# 已定位候选后，按其实际路径读取正文；长文按实际行号取章节
sed -n '1,100p' content/inbox/mysql-explain-extra.md
```

`-m 3` 是首轮控制输出的示例，不是候选总数或完整性保证。命中太多时先只取路径，或增加有区分度的词；不要用 `head` 截掉候选后就判断已查全。发现工具输出截断，应缩小单批范围或分批读取。无匹配（`rg` 退出码 1、`grep` 退出码 1）是正常结果；其他非零退出码是执行错误，需处理，不能当作无内容；不存在的可选目录无需搜索。

## 归属判断与写回

读过候选后，按讨论最终收敛的范围提取要记录的问题、结论与澄清，再为每篇确定一个问题并判断写入位置，不能把整段讨论直接归入同一主题文档。重要追问不等于必须单独建卡，但其形成的有效解释、例子与边界应有归属；探索过但已排除的范围不因出现在对话中就重新展开。篇幅与拆分按 [[docs/writing-style|正文写法]] 判断，不为每段话各建一篇。

| 新内容与已有正文的关系 | 操作 |
| --- | --- |
| 回答同一问题，补充条件、解释、证据或修正 | 更新原文对应位置，保留有效内容与出处 |
| 为原问题服务的附属细节、少量引用或简短参考表格 | 留在原篇，必要时增加小节 |
| 回答独立问题，已有材料需要单独展开，候选仅顺带提及 | 新建笔记，在有意义的提及处连接已有正文 |
| 已有正文完整覆盖，没有新增依据或修正 | 不重复写入，向用户指出已有位置 |
| 与旧结论冲突 | 核对适用条件及双方依据，标明争议或过时，不静默覆盖 |
| 用户要求保存，但内容尚未成形或无法确定归属 | 暂存 inbox，说明待整理或待核实事项 |

新建前，若首轮只查了文件名或属性，补一次正式笔记与 inbox 待处理内容正文的主题词与同义词检索；已经覆盖的检索不重复执行。已有相似候选须读正文后再决定。检索不足或索引故障时不能据此宣称「库内不存在」，应使用文件检索兜底。沿用 `content/` 文件列表核对拟用文件名，遵守 [[docs/metadata-and-links#文件名与属性|文件名与属性]] 的命名规则。

写回前重新核对目标当前内容和工作区已有改动；若其他编辑改变了候选，重新判断合并位置，避免用旧正文覆盖。新建、更新的目录与属性按 [[docs/metadata-and-links|格式与链接规范]] 处理。查询结果引用实际文档，区分库内依据与额外补充。

保存后复用候选和已知引用，仅补搜新概念、被修正的结论及目标链接。新证据改变旧笔记的结论、适用条件或解释时，同步修改实质受影响的位置，不能只在新文中补链接；无实质影响的旧文保持不变。读回差异，对照获准保存的问题检查是否有遗漏或仅剩空泛结论，再检查原意、出处、重复、属性及链接目标与锚点，并完成 [[docs/writing-style#阅读验收|阅读验收]]；移动、合并或重命名还需维护全部入站引用与附件路径。仅格式或属性调整不刷新 updated_at。完成后简短报告实际文件、修改理由、关系维护与待核实事项，不生成额外操作报告，不自动提交或发布。

## 专题入口与阅读组织

知识图谱提供自由跳转，专题入口提供可看全的阅读范围。凡一个话题、子话题或实现方案由多篇文档共同展开，都应有明确入口；已有总览能承担时直接补充，否则建立简短入口。只有一篇的内容由自身承担入口，不为每个术语机械增建空页。

- 入口说明本组要回答什么，区分主线、实践、源码等有意义的分支；列全直接所属卡片或子专题入口，简述各自回答的问题及必要顺序，不只堆标题。
- 子专题入口继续列全本组内容。一个方案可在上级入口中占完整且可锚定的小节；范围变大或需要独立导读时再分篇。上级无需重复列出全部后代。
- 有清晰上下级关系的卡片填写 [[docs/metadata-and-links#元数据|parent 属性]]，直接写主要上级文件名，必要时附带章节；无明确上级时省略，不强行归属。阅读面板在分类旁显示返回导航，不在文末重复添加。横向前置、比较与延伸链接继续保留，但不是发现同组其他文章的唯一路径；跨专题引用不自动成为本组必读。
- 新增、拆分、合并、重命名或归档时，同步维护所属入口及必要上级入口。入口与正文仍分别只维护一份，不复制全文，不以标签聚合或任意路径可达充当覆盖。

验收受影响范围：从入口能直接看全本组，从子文能返回，分支有独立范围且无漏项、失效链接和重复正文。入口变长时按子专题分层，保留完整覆盖；规则生效不等于历史专题已全部整理，全面补齐需按授权范围执行。

## 修改操作

同一问题更新原文，附属细节与少量参考留在原篇；独立问题有足够材料需要展开时才新建。以下是原文已存在、需要改变结构或位置时的操作；每种操作都先查全部入站引用（`node scripts/retrieve.mjs links <文件名>` 一次列出出链、入链与断链），完成后维护受影响的链接与附件路径，并读回检查。

- **合并**：两篇回答同一问题时，选内容更完整的一篇为主，吸收另一篇的有效正文与出处；把指向被合并文档的双链按引用意图改指向主文档并保留显示名，确认无残留后删除或移入 archive。
- **拆分**：一篇承载多个需要独立展开的问题时拆成多篇，各篇只留自己的问题与依据，必要的简短原因、对比和参考仍可留在原篇。拆分后按写作细则维护总领卡片的引导，并把原双链按语义改指向对应文档；既检查目标有效，也检查阅读入口是否仍能找到各部分。
- **重命名**：常规补充保持文件名稳定；内容收敛、拆分或重构后，若旧名已不匹配最终主题，应在本次重构中同步改名。先核对新名唯一，记录旧名到新名及全部入站引用，改名后逐一更新并检查残留、断链与歧义；不因改名自动迁移学习状态目录。
- **归档**：内容当前先精简掉但可能恢复时移入 `content/archive/`；不再恢复时按 [[docs/metadata-and-links#链接与合并|链接规则]] 把入站双链降级为普通文字，保留原句语义。

以上操作保留有效内容与出处、保留原文创建日期、维护附件路径；合并与拆分后检查原链接是否仍指向同一内容，而非只判断目标是否存在。

有效出处指支持知识内容的参考资料，不要求保留对话来源或编辑沿革；不在卡片中追加拆分、迁移或整理说明。

## 冲突与结论维护

区分事实、个人理解、推导与实测，保留关键来源与适用条件。新信息与旧结论冲突时，先核对双方的适用条件、时间与依据，不因来源较新就自动覆盖。需要保留争议时，在原结论处用统一标注记录，便于检索与复核：

```markdown
> **争议**：新结论……；旧结论在其适用条件（……）下仍成立。依据：……。
```

被新来源取代的旧结论用 `> **过时**：……（由 [[新文档]] 取代）` 标注，保留结论与出处，不静默删除历史。跨文档的冲突在双方各自标注并互相链接。未执行或未核实的结论注明「待核实」，不写成既定事实。

## 查询与答案归档

查询时始终先检索再回答，引用实际文档并给出文件名，明确区分「库内结论」与「额外补充」；库内没有依据时说明检索范围与结果，不用记忆冒充库内内容。普通查询不写文件。

答案是对比、综合或可复用的新结论时，Agent 可主动提议保存；用户要求保存后，同样按归属规则处理：回答已有问题就更新原文，形成需要独立展开的问题才新建，已完整覆盖则指出已有位置。引用库内文档时直接链接，不复制被引正文，不因内容来自问答就固定新建归档页。

## 学习反馈与修订

知识库保存、补充或整理完成后，在简短汇报之后，结合本次实际改动与用户反馈，主动提出一两个值得关注的问题；一个学习问题讨论告一段落时也可采用同样方式。按前置知识、当前理解与掌握、适用边界、延伸问题检查，优先提示影响当前理解的缺口，其次才是延伸方向，不必凑齐所有维度。问题应具体，并用一句话说明它为何值得关注；已有笔记能回答时，可直接指向对应内容。没有明确价值时省略，不在每次回复后机械追加。

这些提示呈现在对话中，不作为每张卡片的固定栏目，不自动创建卡片、扩写正文或添加学习属性。用户决定继续、跳过或暂放，当前对话中避免重复提醒已讨论或暂放的问题；提出理解检查不等于认定用户尚未掌握，也不自动开始测验。需要跨会话保留学习进度时，仍按用户的保存要求处理。讨论后的内容依普通归属规则判断：本篇必需的解释或条件在获准后补原文，个人尚未掌握时先讲解，独立延伸问题在用户要求保存后再决定是否新建。

用户说「看不懂」时，先结合正在阅读的段落定位缺口：缺少前置就补最小解释或已有链接；解释跳步就补因果与例子；拆分过细就评估合并或恢复必要上下文。先回应当前疑问；仅在用户要求保存、修改，或已有对应编辑授权时写回，不把每次追问都变成新笔记。新建卡片或首次回答遵循先简后补：先用一句话或一段话说清问题，条件、因果、例子和来源等细节在追问下就地补充，避免一次写满，也避免把追问默认当成新卡片。

用户要求安排学习顺序时，先整体定位、再主要组成、后局部机制；按 [[#专题入口与阅读组织|专题入口]]保留阅读顺序及完整范围，细节复用已有正文，不复制答案或另存一套全文。用户要求深入或跳过时按其意图调整，不以固定顺序阻止继续。需要保存进度时，只记录实际阅读或讲解范围、用户提出的疑问及下一步，按普通保存规则归属；文档状态、事实可信度与个人掌握程度分别处理，不从阅读、讲解或整理完成推断掌握。新建内容默认留在 inbox，用户明确确认本篇所需概念已理解后才迁入 notes；延伸卡片可继续留在 inbox，无需递归学完所有链接目标。

星云目前只提供随机抽取标题、再打开正文的复习入口，尚未记录进度或安排间隔复习。用户需要复习提示时，围绕选定内容提出明确、聚焦的问题，并定位到原文答案；不复制完整答案，不默认给全库生成题库、评分或新增学习字段。讲解与测验按用户请求分别处理。

同类阅读问题反复出现时，先在授权范围内修订具体内容，再按 [[#规则维护|规则维护]] 判断是否需要调整通用规则；不因单篇例外增加全库必填字段或自动展开全面改写。

## 规则维护

用户明确表达长期偏好，或同类使用问题反复出现时，结合实际反馈判断是否需要更新项目规则。单次任务的特殊要求只在当前范围内适用；一次具体方案不自动成为所有任务的唯一做法。用户要求补充或优化规则时，直接在该范围内执行；普通反馈先用于解决当前问题，不自动扩大为规则改写。

提炼前先查对应约定：已有规则明确但未被遵守，先纠正执行；表述不清或存在冲突，在原条目澄清条件；确有缺口，才新增规则。已有内容完整覆盖时不换一种措辞重复追加。规则应说明适用情境、应采取的行为与必要边界，让后续 Agent 能据此作出判断。

规则按作用范围归属：

| 内容 | 存放位置 |
| --- | --- |
| 项目通用约束与必要的规则入口 | AGENTS.md |
| 判断标准、适用条件与示例 | docs 中对应的管理、格式或写作文档 |
| 有明确触发条件、会重复使用的任务流程 | .agents/skills 下的项目 Skill |

每项详细规则只维护一份，入口保留简短约束并链接到细则。Skill 编排操作并引用项目规则，不复制另一套约束；例如「把刚刚讨论的内容整理进知识库」使用 [knowledge-save](../.agents/skills/knowledge-save/SKILL.md) 串起检索、归属、写回与验收。仅有一条偏好或已有流程足以处理的小改动，不必单独建立 Skill。

获准维护后，同步处理实质受影响条目中的冲突、重复和引用，并用一个相关实际任务检查新规则是否能指导判断、是否遗漏原有边界。尚未实际执行的情境检查应注明为推演，不声称已验证行为效果；范围限于改动和受影响内容，不自动展开全库改写。

## 索引的现状与维护边界

`scripts/retrieve.mjs` 是供 Agent 使用的只读检索层，复用 [[apps/web/README|文档阅读页面]] 的解析逻辑（frontmatter、双链、锚点、反链），覆盖 `content/notes/` 与 `content/inbox/`，每次按当前源文件实时生成、不落地缓存，因此不会与正文不一致。子命令：`index` 输出每篇一行的 JSON（不含正文），`query` 返回紧凑候选，`links` 查出入链与断链，`lint` 做结构巡检；它依赖 `apps/web` 的依赖，首次使用前执行 `make install`。

正文仍是唯一内容来源，检索层是可重建的派生视图，不另建与检索数据重复的全库文件清单；供人阅读的专题入口按 [[#专题入口与阅读组织|入口规则]]维护，检索派生视图本身不进入公开发布范围。读取候选和写回始终以当前源文件为准，不能仅凭检索层零命中决定新建；规模明显增大后，再考虑落地持久索引或全文引擎。

## 来源与巡检

自己的内部文档只维护一份正文，新建时放入 inbox；用户明确确认理解本篇所需概念后再迁入 notes，不生成重复原文、数据库快照或迁移备份。外部资料通常只引用链接；用户提供需要保留的原文件或明确要求保存原文时，才建立 `content/sources/`，记录出处、保存时间和版本。图片等附件按需存入 assets。

原文值得保留的情况：页面可能删除或改写；需要固定引用当时的措辞或数据；本地批注、PDF、付费或离线材料无法仅靠链接复现。Agent 可以提出保存理由，普通引用不自动下载整份原文；保存后与整理笔记区分，不再覆盖为总结稿。

冲突结论说明双方依据与条件，不因来源较新就自动覆盖旧结论。实践卡保留环境、步骤和结果，个人想法不强制改写为知识卡。

用户要求巡检时，按下列清单检查；可确定的链接与格式错误直接修复，事实争议先报告：

- **断链与歧义**：双链目标或锚点不存在，或多篇同名导致无法唯一解析。
- **重复**：多篇回答同一问题，或正文高度重叠。
- **孤立**：没有任何入站双链，也未被 README 等入口文档提及；仅作为阅读入口缺失的候选，不为消除孤立而强加链接。
- **元数据**：title、category、tags、type 与日期是否合理，日期是否与正文最后实质变更一致。
- **过时与冲突**：结论已被取代却未标注，或存在无依据的过期内容。
- **格式与写作**：是否违反 [[docs/metadata-and-links|格式规则]] 与 [[docs/writing-style|写作规则]]，是否依赖原始聊天、解释跳步或拆分过细。

链接与元数据的结构性核对可用 `node scripts/retrieve.mjs lint`（或 `make lint`）批量执行，它检查断链与歧义、重复文件名、缺少 frontmatter 与 title、日期、命名、链接写法与孤立文档。巡检只报告结构问题，事实争议由 Agent 判断，不代替人做事实判断。内容默认私人，公开发布须明确授权具体文件；授权文件清单的过滤先于搜索、关系与附件生成，不依赖文档里的可见性字段。

当前实现边界：Pages 导出 notes 与 inbox 的全部文档，尚未实现上述授权过滤。保存笔记不包含公开授权；过滤实现前，只有完整导出范围均获授权才可发布，否则先实现过滤。构建、搜索、关系和附件须使用同一授权范围，不能只在页面上隐藏未授权内容。
