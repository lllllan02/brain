# 标签维护

让同一含义使用一致名称，同时保留有检索价值的区别。本技能只提供标签处理方法；操作范围遵守项目根目录 [AGENTS.md](../../../AGENTS.md)，字段分工与命名以 [文件名、元数据与链接](../../../docs/metadata-and-links.md) 为准。已读且未变化时不重复读取。

## 选择已有标签

- 先理解当前文章的问题与内容，再检查相关笔记已有的 tags。优先用项目检索层找到候选，必要时查看只含元数据的索引；不要为一次标签选择读取全库正文。
- 在项目根运行 `node scripts/retrieve.mjs query <主题词及同义词>`；需核对现有名称时用 `node scripts/retrieve.mjs index`，筛选相关记录的 tags。工具不可用时用 `rg` 定位并读取候选 frontmatter。
- 复用含义一致的已有名称，保留中文和正式技术名称，不强制全部小写或英文。仅提到某个词不代表它适合成为文章标签。
- category 表达唯一归属，type 表达文档类型，tags 服务检索与跨主题关联。不要为了填满固定组合而重复添加领域、类型和项目标签。
- 标签数量由实际用途决定；不设置固定上限，也不因文章缺少标签而补齐。低频、较具体或新出现的标签不自动视为错误。

## 规范已有标签

在用户要求的范围内检查并修正；日常保存只处理当前文档及必要的受影响范围。

1. 找到不同写法对应的文章，结合正文确认是否真正同义。大小写或拼写差异可规范；上下位概念、相关技术不可当作同义词，例如 Next.js 不能直接归并为 React。
2. 有项目明确约定时采用约定名称；没有时依据通用名称和现有用法选择。频次只辅助判断，不决定语义。
3. 仅修改有依据的 tags，保留顺序中有意义的安排、其他属性和正文；去除完全重复项。仅改标签不刷新正文更新时间。
4. 无法判断的项保留，简短说明歧义；继续完成已能确定的部分，不把常规标签选择变成逐项审批。

## 增加新标签

确认已有名称无法准确表达且有检索用途时，可以在当前保存任务内新增，不要求先在多篇文章中出现。笔记 aliases 表示文章别名，不用来存放标签同义词。

现有标签从文件生成，不另建一份需要逐条同步的全量词表。只有用户要求建立约定或当前整理确需长期记录命名决策时，才补充项目格式文档中的名称、含义和同义映射；不自动新建 taxonomy、导航或日志文件。

## 专项检查

用户要求标签审计时，默认检查 `content/notes/` 与 `content/inbox/`；归档、项目规则和技能文件不混入笔记统计。用户指定范围时按其范围执行。

从 frontmatter 统计使用情况，重点检查同义异写、重复、含义不清以及与正文不符的标签。先定位候选，再读相关正文；仅凭计数不能决定合并。输出实际问题、受影响文件及建议；无标签和低频标签可作为观察项，不作为违规项。审计保持只读，只有要求修正时才修改。

## 验收与范围

读回修改后的属性，确认 YAML 有效、标签含义准确、未改动无关内容。按项目验收规则检查实际受影响范围，不因单篇标签修改触发全库巡检。

不依赖外部 llm-wiki、环境变量配置、QMD 或记忆同步命令；文件是唯一内容来源，现有检索层按当前文件生成结果。标签不授予发布权限，内容可见性与发布操作遵守项目规则。
