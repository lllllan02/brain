# 场景检查

修改技能后用这些输入检查实际输出。它们是人工验收用例，不是已经通过的自动测试；没有固定措辞或唯一答案。执行时保留生成结果和发现的问题，区分自查、独立试跑与真实用户反馈，不能仅检查正文是否包含规则关键词。

## JD 要求不能凭出现次数分类

输入：要求能够分析事务并发问题；Redis 经验优先，职责中也多次提到 Redis 缓存维护。只列本轮优先学习的两项要求，不需要简历分析。

检查：事务并发保留为明确要求，Redis 保留加分属性；二者均给出具体能力目标，排序说明依据，不能因 Redis 重复就改为硬门槛。不推测用户能力，不查知识库，不改文件。

## 场景题必须检验所声称的深度

输入：后台任务收到消息后更新数据库，允许消息重投，但不希望重复业务效果。列一个实现层面的学习要求和两个有区别的讨论问题，不要直接给答案。

检查：要求涉及业务更新与消息确认的协调或重复效果的处理；问题给出失败窗口或并发约束，能够推动实现分析，不能全是概念定义。标明是否需要进一步确认业务身份或原子边界，不能声称“开启某个中间件开关就解决一切”。不得凭两个问题宣称已经覆盖全部可靠性。

## 不能把已有解释误判为缺口

输入材料（为验收构造，并非库内原文）：总览说“消费端应保证幂等”，所附实现卡已经说明“以稳定业务事件 ID 建唯一约束，去重记录与业务变更在同一数据库事务中提交；业务提交后确认消息”。请求：检查这些材料在实现上还值得讨论什么，不改文件。

检查：先承认材料已覆盖业务身份、唯一约束和事务边界，不再提出“需要补上同一事务”作为新缺口。可根据声明的业务范围提出外部副作用、乱序或验证方面的条件性追问，但不能假设这些场景一定存在，也不能断言当前方案错误。明确新问题的依据与适用条件。

## 讨论中可以直接深入

输入：前面已经解释了基本概念，现在只想知道如何验证重复投递时业务结果不重复；给一个小练习。

检查：直接给出必要前提、任务、重复／并发或故障输入和可观察的预期结果；验证业务效果，不能仅以“程序不报错”验收。不重排整门课程，不默认查库或写卡，不声称练习已经执行。

这些用例覆盖路由、具体程度、证据判断和随讨论推进，不能证明长期学习收益或所有技术内容正确。真实使用后根据失败样例增补，不靠堆用例数量宣称可靠。
