## 目标与入口

让反馈改变实际交付。遵守 [AGENTS.md](../../../AGENTS.md)，规则归属与记录边界见 [规则维护](../../../docs/knowledge-management.md#规则维护)。本流程嵌入当前任务，不另起一轮知识入库，也不要求用户再次确认已授权的规则维护。

## 接到反馈时

先判断用户在纠正什么：内容是否正确、问题是否回答到、深度是否合适，还是表达和操作方式有问题。用本轮反馈与实际结果定位差距，不把“太长”直接理解为删字，也不把“突出重点”直接理解为增加加粗。

在当前授权范围修正结果，并在本轮结束前处理可复用部分，不等待条目累积：

| 判断 | 动作 |
| --- | --- |
| 仅适用于这篇、这一层或本次任务 | 按当前要求完成，不升级为全局规则 |
| 明确的长期偏好或已查明的可复用失误 | 直接修改对应正式规则或操作环节，无需先写经验条目 |
| 现有规则已覆盖，但结果仍不符合 | 查清是没读到、理解错、操作出错还是验收遗漏；修补实际断点，不再追加同义要求 |
| 原因或适用范围仍不明确 | 先完成能够确定的修正；确有后续动作时才保留活动经验 |

写规则时保留适用条件与选择空间。用户选择表格、图片或一种文风，不自动成为所有任务的固定模板；明确长期偏好则不能被当作一次性意见忽略。写入前重读目标，只改相关条目，保留并行修改。实质修改 Skill 时使用可用的 skill-creator。

## 在后续任务中使用

开始实质工作前，按当前问题读取相关正式规则和[活动经验](../../../.learnings/LEARNINGS.md)。正式规则是执行依据，活动经验只提示尚待处理的问题；没有活动条目也要沿用已落地约定。

把相关要求转成本次结果中可观察的判断，带入写作或操作，并在交付前读回对应结果。例如，比较篇的检查是“开头是否说清关键差异为何适合当前需求”，不是“是否有结论标题或表格”。只选本次适用项，不向用户倾倒检查表，也不为验证流程改写无关文件。

遇到反例或用户再次纠正，回到实际差距：原规则范围过宽就收窄，表达歧义就改原句，执行遗漏就补读取或验收环节。不要因为已经记录过而重复机械执行，也不要把所有例外继续堆成新规则。

## 收尾与未完成事项

对照本轮用户指出的问题检查修改后的内容或行为，再确认有价值的反馈已落到后续会读取的位置。记录“改了哪里、实际检查了什么、还缺什么证据”；写入成功与规则格式检查不能证明行为已改善。没有新经验就结束，不生成例行报告。

只有未解决原因或需要后续实际任务观察时，才在 `.learnings/LEARNINGS.md` 保留一个同问题条目：问题键、范围、简短依据、正式落点、状态，以及“什么任务触发、做什么、看到什么可结束”。记录与归档按[工作经验的记录与合并](../../../docs/knowledge-management.md#工作经验的记录与合并)，不复制规则正文，不为了留痕先建再归档。

下次命中该场景时，在正常任务中完成对应检查。实际通过则收束，失败则修订；当前任务的情境推演与后续独立验证分开记。交付只简短说明实质变化和必要的未验证事项，不以“已反思”作为完成证明。
