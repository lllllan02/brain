**「可独立探索的研究分支能受益于多个上下文窗口，但收益伴随更多推理开销和协调工作。」** 原文发表于 2025-06-13，本文节选分工、评测与运行经验，数字仅代表文中系统。

## 从搜索到汇总

主 Agent 制定并保存计划，把不同方向交给子 Agent；子 Agent 自行搜索、判断资料并压缩发现。主 Agent 汇总后决定是否继续调查，最后由引用处理环节定位证据。各分支不必将全部网页内容带回主上下文。

早期系统会过度创建 Agent、重复搜索或持续寻找不存在的资料。作者因此明确委派目标、输出格式、工具与来源范围，并按任务复杂度约束投入。模糊的「调查某行业」曾导致多个分支重复查同一时期。

## 收益的依据与限制

作者报告 Opus 4 主 Agent 与 Sonnet 4 子 Agent 在内部研究评测中，相对单 Opus 4 提升 90.2%；这不是成功率增加 90.2 个百分点，也不是固定预算下对所有任务的证明。其数据中，多 Agent 系统 Token 用量约为普通聊天的 15 倍，分母并非单 Agent。

强依赖、需要共享大量上下文的任务较难获益。文中同步等待整组结果的实现还会受慢分支阻塞；异步运行能增加重叠工作，也增加状态协调与错误传播难度。

## 怎样让结果可核验？

原文结合结果评估、人工检查与生产 Trace 定位错误，使用检查点避免失败后全量重跑。子 Agent 也可将完整成果存成产物，只返回引用，减少层层转述造成的信息损失。

这些经验支持按任务结构设计协作，不能据此推出「Agent 越多越好」或预设统一并发数。
