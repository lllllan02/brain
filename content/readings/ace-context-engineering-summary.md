**ACE 把可复用策略组织为带标识的条目，通过反思和局部增量更新积累经验，避免反复全文重写抹掉已有细节。** Qizheng Zhang 等人的论文研究上下文适配（Context Adaptation），本文依据 2026-03-29 的 v3。

这里适配的是系统提示或跨任务经验：模型参数不变，输入中的策略随反馈更新。它与[[context-compaction|当前会话历史压缩]]有关联，但不是同一个问题，也不承诺保存全部会话状态。

## 为什么「每轮重新整理经验」会失效？

作者区分两种现象：

- 简短偏好（Brevity Bias）：优化后留下「认真检查」等通用要求，却删掉环境特有的用法、例外和失败经验。
- 上下文坍缩（Context Collapse）：积累较长后，某次全文重写突然输出极短摘要，大量已有知识消失。

论文在 AppWorld 的一个 Dynamic Cheatsheet 案例中，记录到 18,282 token 的上下文下一步缩成 122 token，准确率从 66.7 降到 57.1，低于未适配基线的 63.7。这个案例说明全文重写可能产生突变，不代表所有摘要都会发生相同坍缩。

## 更新链路怎样工作？

现有策略条目 → 执行任务并留下轨迹 → 提取成功与失败经验 → 生成局部更新 → 程序合并条目。

| 角色 | 输入与输出 | 为什么分开 |
| --- | --- | --- |
| Generator，执行者 | 使用当前策略解题，产出行动与结果，指出有用或误导的条目 | 提供具体轨迹，而非凭空编写经验 |
| Reflector，反思者 | 根据轨迹、执行结果及可用答案提取经验，可多轮修订 | 单独判断错在哪里、什么可以复用 |
| Curator，整理者 | 将经验组织为增量条目 | 只提出新增或局部修改，避免重新生成整份历史知识 |

条目包含唯一 ID、有用／有害计数及策略内容。轻量程序确定性地合并更新，新增条目使用新 ID，旧条目原位更新；语义去重控制重复。整理可以每次更新后进行，也可以接近窗口限制时再执行。

这里有两个不同保证：程序合并能保护未修改条目的存在，不能保证模型新提出的经验正确。条目 ID、反馈和局部操作使错误更容易定位，可信度仍依赖反馈质量。

## 实验怎样区分「学到了」与「看到答案」？

主实验用同一个 DeepSeek-V3.1 承担三个角色，避免由更强反思模型向较弱执行模型传递能力。AppWorld 测 API 理解、代码与环境交互；FiNER 和 Formula 分别测金融实体标注与计算，附录补充其他领域及模型。

- 离线适配：在训练集积累策略，然后到测试集评估。
- 在线适配：对一个测试样本先作答，再用该样本反馈更新，后续样本才使用更新后的经验；各方案使用相同打乱顺序。
- 无真实标签：在 Agent 环境中仍可利用执行成败；无标签不等于没有反馈。

附录 A.5 固定 AppWorld、DeepSeek-V3.1 和离线适配，对增量更新做消融：

| 方案 | test-normal 任务目标完成率 TGC | 场景目标完成率 SGC |
| --- | --- | --- |
| ReAct 基线 | 63.7 | 42.9 |
| ACE，去掉增量更新 | 67.3 | 46.4 |
| ACE，保留增量更新 | 76.2 | 64.3 |

这比只看 ACE 相对其他系统的排名更直接支持「更新方式有贡献」。反思、多轮训练和预热也有独立消融；增量更新并不是唯一变量。

## 有效经验怎样变成有害记忆？

如果反思者没有可靠答案或执行反馈，就可能把错误解释写成经验。FiNER 的在线无标签实验中，ACE 准确率为 67.3，低于基础模型的 70.7；同一设置在 Formula 上却改善。因此，是否有可校验的反馈会影响适配结果，不能以「持续反思」保证持续进步。

作者也明确指出，某些任务只需要短指令或单条规则，长策略库会冗余。ACE 更适合需要环境细节、复杂工具用法和领域经验的任务。

## 成本应分哪两部分？

适配成本是获取轨迹、反思和更新策略的支出；使用成本是后续把策略带入模型的支出。论文报告局部更新减少前者，缓存复用缓解后者，但更长策略仍占窗口。不能把「适配更快」直接写成「每次推理都更便宜」。

阅读判断：它与 [[chroma-context-rot-summary|Context Rot]] 并不简单矛盾。ACE 增加的是经反馈整理的相关策略，Chroma 检查的包括无关内容与干扰。要比较，需固定任务并检查新增条目的边际收益，而非只比较输入长度。
