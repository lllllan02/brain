**有效的 Agent 工具，应让模型容易选对、填对参数并理解结果，再用真实任务评测验证这些设计。**

## 按任务划分工具

机械地把底层 API 全部暴露出来，会让模型承担搜索、拼接和阅读的成本。作者建议围绕常见任务组织工具：例如直接检索相关日志，或封装适合合并的确定性步骤，而不是让模型逐条获取全部数据。

工具数量少不等于设计好；关键在于职责清楚，并让模型用合理的调用完成任务。

## 描述与返回值怎样帮助下一步

名称和说明应交代工具做什么、参数含义及使用边界；工具较多时可用服务或资源前缀避免混淆。返回值应保留继续操作需要的标识，同时通过筛选、分页或详细程度选项减少无关数据。错误信息也应帮助模型修正下一步，而不只是报告失败。

## 用任务评测修正设计

原型 → 代表性任务 → 检查真实调用记录 → 调整工具 → 独立任务验证。

同时观察完成质量、调用次数、耗时和 Token。不能只听模型对失败原因的解释，也不应把唯一调用路径当作成功标准。这些是作者的工程经验，具体粒度与返回格式仍需在自己的任务上检验。
