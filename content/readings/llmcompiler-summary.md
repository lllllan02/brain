**LLMCompiler 让模型先生成带依赖的工具调用计划，再由程序调度执行，从而减少逐次调用模型的开销，并让独立任务并行。**

## 为什么需要执行计划

论文对比的 ReAct 流程是「模型决定一步 → 调用工具 → 结果交回模型 → 决定下一步」。即使两次查询互不依赖，也可能串行等待，并反复支付模型推理和上下文开销。

例如比较两家公司的市值：两次查询可以同时进行，比较计算则必须等两边结果齐备。LLMCompiler 把这种关系显式写入计划。

## 计划如何执行

- 规划器（Planner）由模型生成任务、参数及依赖，后续任务用占位变量引用前序结果，形成有向无环图（DAG）。
- 任务提取单元（Task Fetching Unit）用真实结果替换占位变量，只分发依赖已满足的任务；这一步由程序完成，无需额外模型推理。
- 执行器（Executor）异步调用工具，把结果交给依赖它的任务，最终汇总回答。

**规划与执行还可以重叠。** 流式规划让已生成且依赖就绪的任务立即启动，不必等待整张图，从而隐藏一部分规划耗时。[流式规划](https://arxiv.org/html/2312.04511v3#S4.SS2)

如果执行流程要根据中间结果才能确定，则将结果交回规划器，生成新一轮任务与依赖；这是动态重规划，解决的是初始计划不能预知全部后续步骤的问题。[动态重规划](https://arxiv.org/html/2312.04511v3#S3.SS4)

## 实验说明了什么

论文在多种任务上测试，相对 ReAct 报告最高约 3.7 倍加速，但收益随任务与模型变化。例如 HotpotQA 的 GPT 实验中，与加强提示的 ReAct 基线相比，耗时从 7.12 秒降至 3.95 秒，准确率分别为 62.47% 与 62.00%，并非每项指标都提高。[表 1](https://arxiv.org/html/2312.04511v3#S5.T1)

它的核心收益来自减少模型往返、利用独立分支，以及重叠规划与执行。计划仍由模型生成，依赖判断可能出错；这些基准结果也不代表任意工具任务都能同等加速。未在本地复现实验。
