**Agent 意图识别（Intent Recognition）是把用户表达转换成程序可处理的任务、参数与约束的过程。**

## 为什么需要意图识别？

自然语言没有直接指定程序该执行什么。意图识别提取任务、对象与条件，避免把「能退款吗」当成退款指令，或漏掉「免费才退」的限制。目标不清时澄清，缺参时补齐，超出范围时回退；识别结果仍须经过业务与权限校验。

## 所有 Agent 都需要意图识别吗？

**「理解目标不等于需要独立的意图分类模块。」**

- 多业务入口：可显式分类，用于流程分派和分类评测。
- 通用 Agent：可在回答、规划或工具选择中完成目标理解，无需先输出固定标签。
- 任务已明确的专用 Agent：可直接执行；按钮、表单或上游已提供结构化动作时，无需重新分类。

独立分类会增加延迟、成本与误判点，应按分流需求设置，不必让每个 Agent 重复识别。

## 类别按什么边界划分？

先列出业务动作，再决定标签。订单号属于参数，查询与提交属于不同动作；「订单 A 退款」和「订单 B 退款」不应拆成两个标签。[[azure-clu-intent-design|Azure CLU 的类别设计]]用动作与对象分开表示来避免类别膨胀。

| 用户表达 | 识别结果 | 程序下一步 |
| --- | --- | --- |
| 退款规则是什么 | `refund_policy` | 查规则并回答 |
| 订单 A 能退吗 | `refund_eligibility`，对象 A | 校验订单归属后查资格 |
| 帮我退订单 A | `refund_submit`，对象 A | 进入申请流程，检查资格和执行条件 |
| 订单 A 处理一下 | `unclear`，对象 A | 问清动作 |
| 帮我改签机票 | `unsupported` | 说明范围或转交 |

同样一句「确认」也不能在所有状态下都表示退款。[[dialogflow-intent-design|Dialogflow CX]]通过当前页面和流程限制可匹配路由；自建系统可借鉴这一做法，将「当前任务、正在询问的字段、可接受动作」作为判断条件。

## 怎样把用户表达变成意图标签？

类别确定后，还需要一种方法判断用户的话属于哪一类。例如「订单 A 能退吗」应识别为查询退款资格。常见的实现有三种：

**规则（Rule）是人工编写的匹配条件。** 程序检查用户表达是否符合预设的关键词或句式，例如将「订单……能退吗」匹配为查询退款资格。

**文本分类器（Text Classifier）是把文本分到预设类别的模型。** 这里指用「用户表达与正确标签」配对样本训练的专用模型；训练后，它根据学到的文本特征预测新表达属于哪一类。

**大语言模型（Large Language Model，LLM）是能够理解和生成语言的通用模型。** 用于意图识别时，把类别含义、示例和用户表达放入提示，让模型返回标签；也可以要求它同时提取订单号等参数。

### 三种方法怎样选择？

三者可以替换，也可以组合；没有必须依次经过三层的要求。以下是订单客服的选型判断，需用自己的流量验证。

| 条件 | 起步方案 | 主要代价与调整信号 |
| --- | --- | --- |
| 固定命令、按钮或明确句式 | [[intent-rules\|规则]]，直接匹配并记录命中原因 | 表达变化大时漏匹配；正常请求回退过多就重新评估 |
| 类别稳定，已有可持续标注的样本 | [[intent-text-classifier\|文本分类器]]，离线训练、在线预测 | 数据和标签维护成本；相邻类持续混淆时先修数据边界 |
| 冷启动、表达复杂或类别经常变动 | [[intent-llm\|LLM]]，类别定义与示例加结构化输出 | 延迟、调用成本和语义误判；需用实际测试比较模型 |

混合方案可以让固定命令走规则，未覆盖的自由表达走模型。规则命中错误时，后面的模型可能根本没有机会纠正，因此不能只统计整体命中率，要分别看每条路径的错误。

独立分类调用适合先分配到不同业务流程；已有少量工具时，也可直接借助[[tool-calling|工具调用]]表达任务选择。[[langgraph-intent-routing|LangGraph 的路由实现]]展示了「模型产出标签 → 程序选择节点」，普通 `switch` 也能完成这层职责，不必额外建立一个意图 Agent。

## 多轮、缺参和多个目标怎样处理？

「帮我查能不能退 → A → 说错了，是 B」需要[[intent-dialogue-state|参数与多轮状态]]保留目标、替换对象，并使旧查询结果失效。查不到订单事实时应查询业务系统；缺订单号时问订单号；动作含糊时才做[[intent-clarification|意图澄清与回退]]。

「查资格并解释手续费」包含多个目标，「免费才退」包含执行条件。当前三个最小识别器主要覆盖单任务：不支持的复合请求应明确回退，不能只留 `refund_submit` 而丢掉条件。支持后需要把目标与条件绑定，再由[[agent-planning|规划]]安排依赖。**待展开：** 多目标拆解和条件执行的完整实现；现有状态示例仅说明应保留哪些信息。

## 上线以后怎样判断问题在哪里？

[[intent-evaluation|意图识别的评测与上线]]从标注样本、分类与槽位指标、阈值扫描讲到影子流量和回滚。错误排查按层进行：用户目标标对了吗，识别结果对了吗，路由映射对了吗，对象和状态对了吗，业务接口成功了吗。

讨论一套设计时，应能解释选择识别器的依据、无样本时怎样起步、未知请求如何退出、用户改口怎样处理，以及改模型后如何防止回归。回答应落到输入、分支、状态和验证数据，不能只说「加一个大模型理解用户」。本专题代码是教学基线，尚未构成经过真实业务验证的生产服务。
