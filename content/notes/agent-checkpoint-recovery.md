**检查点（Checkpoint）是运行到某个边界时保存的状态记录，包含继续任务需要的数据和执行位置。**

**中断恢复是运行系统读取已保存的进度，重新调度未完成工作的机制。** 它既可用于故障后继续，也可承接[[agent-human-in-the-loop|人工介入]]：今天保存待审草稿，明天收到决定后继续发布。

## 为什么保存对话还不够？

假设 Agent 已写好草稿，正在等人批准。进程重启后，对话能帮助模型理解任务，却未必能可靠区分「还没批准」「已经批准但没发布」「发布成功但回执没保存」。让模型重新猜测或生成，还可能改变被审核的正文。

因此，要把草稿、批准结果和当前步骤显式保存。模型提出内容与动作，程序根据这些执行事实决定等待、调用工具还是结束。这样，换一个进程也能接手同一个任务。

## 保存以后，程序怎样继续？

最小流程是「保存等待点 → 结束当前运行 → 收到回复 → 更新状态 → 新运行执行后续步骤」。等待期间不必保留原来的连接、线程或锁。

[[agent-checkpoint-runtime|检查点的保存与调度]]用一份草稿说明保存哪些字段、何时提交、谁来唤醒任务，以及多个工作进程怎样避免互相覆盖。对应的[[agent-resume-practice|Go 审批示例]]把保存、回复和执行做成独立命令，可以直接观察进程之间如何传递进度。

恢复只能从程序定义的边界继续，不会自动复原任意代码行。更关键的是：如果发布已经成功、本地还没保存回执，恢复时仍可能再次发布。[[agent-resume-failure|恢复时的重复执行实验]]解释这个窗口，以及稳定操作 ID 能解决什么、不能解决什么。

## 框架替我们保存什么？

[[langgraph-checkpoints|LangGraph]]保存图状态和后续节点；[[temporal-durable-execution|Temporal]]保存事件历史，通过重放工作流重建状态。前者适合已有图式 Agent，后者可承接跨服务的长期流程；两者都仍需要业务处理审批与外部副作用。

[[agent-temporal-approval|Temporal 的 Go 审批接入]]展示如何把文件状态机换成 SDK 的持久等待。选框架时要核对恢复粒度：LangGraph 人工中断会重跑所在节点，Temporal 重放会复用已记录的外部任务（Activity）结果，但任务本身仍可能重试。主动选旧检查点重做则属于[[langgraph-time-travel|历史重放与分叉]]，不能当作无副作用的回看。
