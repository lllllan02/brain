**A2A（Agent2Agent）是独立 Agent 系统之间交换能力描述、消息、任务状态与产物的开放协议。** 通信双方可以使用不同框架、模型和内部工具，不必公开彼此的内部实现。

泛称的 agent-to-agent 可以指任何 Agent 间通信；本文的 A2A 专指 Agent2Agent 协议，依据 [[a2a-protocol-specification|1.0.0 规范及官方导读]]，核对日期为 2026-10-13。

## 为什么普通请求响应还不够？

假设采购助手需要供应商 Agent 调查一批零件的交期。直接调用一个 HTTP 接口也能完成通信，但双方还要约定：怎样知道对方能处理哪些零件、任务较长时怎样查进度、缺少规格时怎样追问、最终报价如何交付。

A2A 为这些交互提供共同语义，减少每对服务重复约定。客户端把目标交给对方，对方自行组织内部处理；这与调用本地子 Agent 的运行入口不同。A2A 本身既不部署远端服务，也不替它启动模型循环。

## 一次协作怎样推进？

基本过程是：获取 Agent Card → 核对能力与认证要求 → 发送任务消息 → 取得直接答复或 Task → 获取进度、补充输入 → 收取产物并验收。

| 对象 | 在交期调查中的作用 | 易混边界 |
| --- | --- | --- |
| Agent Card | 描述可调查的范围、接入接口与认证方式 | 能力声明不能证明身份可信或调用已获授权 |
| Message / Part | 传零件规格、询问缺失条件；内容可为文本、文件或结构化数据 | 消息与内容载体不等于最终成果 |
| Task | 跟踪这一轮调查的状态 | 一个任务不等于整个长期会话 |
| Artifact | 返回报价单或交期表等成果 | 收到产物后仍需检查完整性与业务条件 |

能立即回答的请求可以直接返回 Message。需要持续处理的工作返回 Task，客户端可以轮询、接收流式更新，或在服务支持时配置推送通知。选择取决于延迟要求、连接寿命和回调可达性；流式传输不代表业务处理已经完成。

## 追问、任务完成与断线如何区分？

调查缺少零件规格时，任务可进入等待输入状态；需要额外认证时可等待认证。补齐条件后继续同一项未终结任务。这里用语义描述状态，具体枚举和字段以选定 SDK 版本为准。

`taskId` 指定一项工作；`contextId` 关联一组相关任务与消息。例如第一轮报价结束后要求更换数量重新报价，应新建任务，可沿用 context 并引用原任务。**「终态任务不会因为再次发消息就恢复运行。」**

网络断开只说明客户端失去连接，不说明远端失败。客户端应先查询已知任务状态，再决定是否重发或新建任务；A2A 不强制所有发送操作幂等。取消请求也可能失败，已产生的外部效果仍需业务系统核对，不能把超时、取消与回滚视为同一件事。

## 与 MCP、普通 API 和子 Agent 怎么选？

| 方式 | 主要接口职责 | 适合什么条件 |
| --- | --- | --- |
| 本地函数／SDK／图节点 | 调用受同一应用管理的能力与运行 | 内部集成，生命周期可统一管理 |
| 自定义 HTTP API／消息队列 | 按双方约定传请求或事件 | 参与方少、业务契约固定；自行定义状态与成果语义 |
| [[mcp|MCP]] | 发现与使用工具、资源和提示模板 | 希望应用复用统一能力接口 |
| A2A | 面向独立 Agent 服务协商与跟踪任务 | 跨框架或团队，需要共同的任务交换约定 |

MCP 服务内部可以封装 Agent，远端 Agent 也可以用 MCP 访问工具。不能用「是否远程」或「是否调用了模型」区分两种协议；应看外部接口暴露的是工具能力还是独立 Agent 的协作任务。

[[agent-subagents|子 Agent]]是委派关系，A2A 是通信协议；一个主 Agent 可以将 A2A 客户端包装为可调用能力，因此二者能够组合。协议也不要求全网状拓扑，主从、路由或点对点组织均可使用它。

## 接通协议后还有哪些责任？

业务应用仍需选择可信服务、限制数据范围、检查返回成果，并维护跨系统任务标识与 Trace 的对应关系。这里的工程判断是：协议能统一消息格式，不能替应用解决错误分工、过期证据、冲突写入或重复业务效果。

Agent Card 的认证要求是接入条件，实际权限由服务端与下游系统执行。接收文件、URL 或自然语言报告时，也不能把对方的内容自动提升为本地执行指令。

1.0.0 将公共模型和操作映射到 JSON-RPC、gRPC、HTTP+JSON/REST 等绑定。接入前应固定协议与 SDK 版本，并按声明核对可选能力；旧教程中的字段、方法名和传输假设不能直接混用。
