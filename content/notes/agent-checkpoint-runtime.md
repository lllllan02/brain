Agent 已生成草稿，准备等待审核。要让当前进程退出后仍能继续，需要保存一份**「新进程读到后，就能决定下一步」**的记录。保存消息只是其中一部分，还要保存控制状态。

## 一份记录怎样确定下一步？

下面是自建状态机的字段分工；具体存储可合并或拆表，不是框架固定格式。

| 内容 | 草稿例子 | 少了会怎样 |
| --- | --- | --- |
| 任务身份、数据与流程版本 | `task_id`、记录格式版本 `schema`、流程版本 | 找错任务，或用新代码误解旧数据 |
| [[agent-task-state\|任务数据]]及结果 | 冻结草稿、目标、工具回执 | 重新生成改变已审核内容 |
| 状态与等待点 | `waiting`、审批 ID、期限 | 不知道等什么、下一步做什么 |
| 外部操作 ID | `operation_id` | 重试被当成新操作 |
| 状态版本与执行归属 | `revision`、领取标识 | 旧运行覆盖新结果或重复接续 |

连接、锁和 goroutine 不进入记录；恢复时重新创建。大产物可存不可变引用，但引用内容必须保持可用。[[langgraph-checkpoints|LangGraph 的快照]]用状态值、后续节点和任务记录表达类似的控制需要。

## 谁在什么时候保存？

工作进程（Worker）负责执行，调度器负责发现并分派可执行任务。草稿发布可采用 `waiting → ready → executing → done`，每次迁移都对应一个已确认的事实：

1. Worker 将草稿、审批单和 `waiting` 一起提交，再展示待审事项并退出。不能先让人看到请求，随后才尝试保存。
2. 回复入口校验决定，把批准和 `ready` 一起提交。拒绝则写终止状态，不进入执行分支。
3. 调度器领取 `ready`；Worker 检查当前条件，确认操作 ID 已保存，写入 `executing` 后调用工具。
4. 收到回执，把结果与 `done` 一起提交。后续模型输入使用这个已保存结果。

若只写了草稿、没写下一步，恢复可能再次生成；只写了完成状态、没写回执，后续总结又缺少依据。因此同一个本地步骤的结果与控制状态应原子提交。检查点越细，失败后重做越少，但保存成本越高；优先选择成本高的步骤完成后、进入等待前及外部操作边界。

## 状态已保存，任务为什么还可能不动？

回复入口可能提交 `ready` 后、发送唤醒通知前崩溃。自建调度器可以周期扫描可执行状态，或在同一事务中写入待发送事件，再由发送器重试。通知加快响应，持久状态决定是否还有工作。

长时间等待不能一直持有事务和资源锁，否则会占用连接并阻塞其他工作。数据库事务只跨越短暂的状态变更；跨进程等待由持久记录承担。

## 多个 Worker 或新版代码怎样接手？

状态版本用于条件更新，防止旧运行覆盖新状态；领取任务还需排他机制。租约是一种带期限的执行资格，过期允许其他 Worker 接手，但旧 Worker 可能仍活着。存储或执行端可检查递增执行代次，拒绝失效执行者；无法检查的远端操作仍需幂等控制。

新代码读取旧任务时，要判断 schema 与流程是否兼容；不兼容就保留旧执行器、迁移记录或停止并人工处理。恢复前重查权限、凭据及资源条件，取消、超时和无法恢复要有明确结果。

这些措施保证本地调度有据可依。远端写入和本地提交仍是两个时点；[[agent-resume-failure|重复执行实验]]继续处理「工具成功了，回执还没保存」的情况。
