**检查点（Checkpoint）是在明确执行边界持久保存的一份状态记录，包含恢复任务所需的数据与执行位置。**

设计 Agent 检查点，要先确定两个问题：**「中断后允许从哪里重做」**，决定什么时候保存；**「新进程从那里继续需要知道什么」**，决定保存什么。下面先沿模型与工具的调用循环确定保存位置，再以「生成草稿 → 审批 → 发布」说明状态与调度。

## 什么时候保存？

对于「模型决定下一步 → 执行工具 → 将结果交回模型」的 Agent，可以在**接收输入后、每次模型完整返回后、每次工具结果返回后**保存进度；需要审批或补充信息时，再保存等待状态与恢复输入。下面是一种自建 Agent 的保存方案，具体边界还要与框架的执行方式对应。

| 保存时机 | 保存什么 | 恢复后做什么 |
| --- | --- | --- |
| 收到用户输入后、首次调用模型前 | 本轮输入、必要上下文、下一步为模型调用 | 重新发起模型调用，不丢失本轮任务 |
| 模型完整返回后、执行工具前 | 模型响应、工具调用 ID、工具名、参数及待执行列表 | 使用已确定的调用，不让模型重新决定工具与参数 |
| 发布等外部写操作执行前 | 确定的操作参数、稳定操作 ID、已校验的审批结果和 `executing` 状态 | 核对或重试同一次操作；不能仅凭本地状态判断远端是否成功 |
| 每个工具返回后、结果交回模型前 | 与调用 ID 对应的结果、成功或失败状态、剩余待执行项 | 复用已有结果，处理剩余工具或继续调用模型 |
| 展示待审事项或问题、暂停等待前 | 待审批草稿版本、审批单或待回答问题、`waiting` 状态 | 继续等待原事项，不重新生成草稿或擅自执行工具 |
| 收到有效恢复输入后、继续执行前 | 补充信息或审批决定，以及 `ready` 或终止状态 | 使用已保存的决定继续；拒绝时终止相应操作 |
| 模型给出最终回答后 | 完整回答和任务完成状态 | 返回已有回答，不重新运行整个任务 |

**相邻调用可以共用一个检查点。** 模型返回后保存的工具调用，也是工具执行前的恢复依据；工具结果保存后，也是下一次模型调用前的恢复依据。若生成草稿后立即等待审批，可以一起保存草稿和等待状态。审批、参数转换或操作 ID 分配若发生在这次保存之后，则需在实际发布前补存新增状态。

### 每次调用都能从中间继续吗？

模型调用前保存，只能留下重新发起请求所需的信息。模型已经返回、响应却尚未落盘时崩溃，通常仍须重新调用，结果也可能变化；流式输出了一半，并不意味着检查点能恢复模型内部的生成进度。

工具调用也有粒度差异。模型一次要求调用 A、B、C 三个工具，A、B 成功后 C 失败：若只在整批结束后保存，A、B 的结果可能丢失；若每个工具的结果都已独立持久保存，恢复时就能复用 A、B，只处理 C。要做到「每个工具完成后保存」，必须有逐工具完成记录，不能只在包住整批工具的外层步骤保存一次。

即使工具前后都保存，仍有「远端发布成功 → 本地回执尚未保存 → 崩溃」的窗口。恢复时需要用原操作 ID 去重或查询远端结果，不能把缺少回执当成未执行。

### 框架会自动在这些位置保存吗？

[[langgraph-checkpoints|LangGraph]]在超级步（同一轮调度的节点执行）边界形成完整检查点，并保存节点完成后的输出用于故障恢复。将模型与工具执行拆成独立节点，才能让图层保存边界对应这些阶段；一个节点内部连续调用多次模型或多个工具，不能仅凭图层检查点保证逐次保存。节点输出记录用于恢复已完成工作，与整步的完整检查点不同。

[[eino-checkpoints|Eino]]支持节点执行前、执行后以及节点内部动态触发中断并保存。这里的「前后」是配置的中断位置；配置存储不等于正常循环里的每次模型、工具调用都会自动落盘。

### 保存成功后才能进入下一步吗？

需要把某个边界作为可靠恢复点时，应等持久化成功再继续。LangGraph 的 `sync` 模式在下一步开始前完成写入；`async` 与下一步并行，突然崩溃可能丢失尚未写完的进度；`exit` 在退出时保存，不能据此保证中途崩溃仍有逐步进度。

**步骤结果与执行位置应一起提交。** 若草稿保存了、下一步没保存，恢复可能再次生成；若完成状态保存了、回执没保存，后续又缺少结果。自建时可以用数据库事务原子提交。

保存越密，通常重做越少，但写入与等待成本越高；可重复、成本低的步骤可以合并保存。定时保存仍须落在一致的状态边界，不能截取尚未完成的状态变更；仅在正常退出时保存则无法应对突然崩溃。

## 保存什么内容？

判断标准是：**「假设当前进程的内存全部丢失，新进程只读这份记录，能否判断该等待、继续还是核对结果，并拿到执行所需的数据？」**

| 内容 | 草稿例子 | 恢复时的用途 |
| --- | --- | --- |
| 任务身份与格式、流程版本 | `task_id`、`schema_version`、`workflow_version` | 找到任务，并确认当前代码能读懂和执行旧记录 |
| 继续执行所需的业务数据 | 目标、约束、必要消息、冻结的草稿版本 | 保持任务要求，复用已有产物 |
| 执行位置与等待条件 | `status`、下一步、审批 ID、期限、审批决定 | 确定从哪里继续，以及是否满足继续条件 |
| 外部操作及其结果 | 稳定的 `operation_id`、调用参数、发布回执 | 核对或重试同一次操作，并复用已确认结果 |
| 并发控制信息 | 状态版本 `revision`、领取者、租约期限、执行代次 | 防止多个运行互相覆盖或同时接手 |

这些是信息分工，不要求全部放在同一行记录，也不是框架固定字段。[[agent-task-state|任务数据]]说明「要做什么、已有何种结果」，执行位置说明「程序现在该做哪一步」；只存聊天记录，未必能可靠表达后者。

无需保存整个进程内存。连接、锁和 goroutine 在恢复时重新创建；大文件可保存不可变版本的引用，但引用内容必须持续可读。需要复用的模型输出和工具结果应保存原值或可靠引用，不能指望重新调用得到相同内容。

## 自己实现，需要做什么？

检查点存储只负责留下记录，还需要执行程序解释记录、找到任务并继续处理。可以按以下职责实现，模块不必拆成独立服务：

1. 定义状态与恢复分支。明确每个状态允许的下一步。例如 `waiting` 继续等待，`ready` 可以领取执行，`executing` 先核对外部操作结果，`done` 复用结果。取消、超时、拒绝和无法恢复也要有明确状态与处理方式。
2. 实现保存与读取。序列化上述数据，用事务一起提交结果和状态；更新时带上预期 `revision`，只有版本仍匹配才写入并递增版本，防止旧执行覆盖新结果。读取时校验格式与流程版本，不兼容就迁移、交给旧执行器或停止并人工处理。
3. 实现恢复入口与调度。审批入口校验决定是否对应当前草稿，持久更新为 `ready`；调度器扫描可执行任务，再交给工作进程（Worker）分派到对应步骤。通知可以加快唤醒，但不能成为唯一依据：提交后、通知前崩溃时，扫描仍应能发现任务；也可在同一事务写入待发送事件，由发送器重试。
4. 实现任务领取与失效处理。多个 Worker 通过条件更新排他领取；租约到期后允许接手。旧 Worker 可能仍在运行，因此写回时还要检查执行代次，拒绝失效执行者。等待审批期间不保留长事务或资源锁，恢复执行前重新检查权限、凭据和资源条件。
5. 处理外部操作的重复执行。首次调用前保存稳定操作 ID，恢复后仍使用它，并由接收端去重或查询原结果。远端成功、本地回执尚未保存时，检查点无法单独判断是否已经发布；无法核对的任务应进入「结果未知、等待核对」，具体边界见[[agent-resume-failure|中断恢复中的重复执行]]。

验证时要真的终止进程并重新启动，分别检查：进入等待后能否恢复、批准后通知丢失能否继续、外部调用成功但回执未保存时是否重复产生效果，以及两个 Worker 竞争时旧执行能否覆盖新状态。以上是设计说明，尚未实现或运行这些验证。
