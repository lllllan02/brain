**检查点（Checkpoint）是在明确执行边界持久保存的一份状态记录，包含恢复任务所需的数据与执行位置。**

设计 Agent 检查点，要先确定两个问题：**「中断后允许从哪里重做」**，决定什么时候保存；**「新进程从那里继续需要知道什么」**，决定保存什么。下面以「生成草稿 → 审批 → 发布」为例，说明一种自建状态机设计。

## 什么时候保存？

检查点放在能够明确判断「哪些工作已完成、下一步是什么」的边界。仅按时间间隔保存，可能截取到尚未完成的状态变更；仅在正常退出时保存，又无法应对突然崩溃。

| 保存时机 | 草稿发布中的记录 | 为什么放在这里 |
| --- | --- | --- |
| 成本高或结果需要复用的步骤完成后 | 保存生成的草稿和后续步骤 | 避免重新调用模型，产生不同草稿 |
| 进入等待之前 | 将草稿版本、审批单和 `waiting` 一起保存，再展示待审事项 | 进程退出后仍知道等谁审批、审批哪份内容 |
| 等待条件满足后 | 校验批准决定，将决定和 `ready` 一起保存 | 已批准的任务能够被重新发现并继续；拒绝则进入终止状态 |
| 外部写操作之前 | 保存操作 ID、确定的调用参数和 `executing` | 恢复后能够识别并核对同一次发布 |
| 外部操作返回之后 | 将发布回执和 `done` 一起保存 | 后续直接复用结果，不再次发起已确认完成的操作 |

这些时机可以合并：若生成草稿后立即等待审批，一次提交即可同时保存草稿和等待状态。检查点越密，故障后需要重做的工作通常越少，但写入与等待成本越高；可重复、成本低的步骤可以合并保存。

**「本地步骤的结果与执行位置必须一起成立。」** 若草稿保存了、下一步没保存，恢复可能再次生成；若 `done` 保存了、回执没保存，后续又缺少结果。自建时可以用数据库事务原子提交。需要以这次保存作为恢复保证时，应等持久化成功再继续；异步写入尚未完成的进度仍可能丢失。[[langgraph-checkpoints|LangGraph 的持久化模式]]也区分了这类时机与保证。

## 保存什么内容？

判断标准是：**「假设当前进程的内存全部丢失，新进程只读这份记录，能否判断该等待、继续还是核对结果，并拿到执行所需的数据？」**

| 内容 | 草稿例子 | 恢复时的用途 |
| --- | --- | --- |
| 任务身份与格式、流程版本 | `task_id`、`schema_version`、`workflow_version` | 找到任务，并确认当前代码能读懂和执行旧记录 |
| 继续执行所需的业务数据 | 目标、约束、必要消息、冻结的草稿版本 | 保持任务要求，复用已有产物 |
| 执行位置与等待条件 | `status`、下一步、审批 ID、期限、审批决定 | 确定从哪里继续，以及是否满足继续条件 |
| 外部操作及其结果 | 稳定的 `operation_id`、调用参数、发布回执 | 核对或重试同一次操作，并复用已确认结果 |
| 并发控制信息 | 状态版本 `revision`、领取者、租约期限、执行代次 | 防止多个运行互相覆盖或同时接手 |

这些是信息分工，不要求全部放在同一行记录，也不是框架固定字段。[[agent-task-state|任务数据]]说明「要做什么、已有何种结果」，执行位置说明「程序现在该做哪一步」；只存聊天记录，未必能可靠表达后者。

无需保存整个进程内存。连接、锁和 goroutine 在恢复时重新创建；大文件可保存不可变版本的引用，但引用内容必须持续可读。需要复用的模型输出和工具结果应保存原值或可靠引用，不能指望重新调用得到相同内容。

## 自己实现，需要做什么？

检查点存储只负责留下记录，还需要执行程序解释记录、找到任务并继续处理。可以按以下职责实现，模块不必拆成独立服务：

1. 定义状态与恢复分支。明确每个状态允许的下一步。例如 `waiting` 继续等待，`ready` 可以领取执行，`executing` 先核对外部操作结果，`done` 复用结果。取消、超时、拒绝和无法恢复也要有明确状态与处理方式。
2. 实现保存与读取。序列化上述数据，用事务一起提交结果和状态；更新时带上预期 `revision`，只有版本仍匹配才写入并递增版本，防止旧执行覆盖新结果。读取时校验格式与流程版本，不兼容就迁移、交给旧执行器或停止并人工处理。
3. 实现恢复入口与调度。审批入口校验决定是否对应当前草稿，持久更新为 `ready`；调度器扫描可执行任务，再交给工作进程（Worker）分派到对应步骤。通知可以加快唤醒，但不能成为唯一依据：提交后、通知前崩溃时，扫描仍应能发现任务；也可在同一事务写入待发送事件，由发送器重试。
4. 实现任务领取与失效处理。多个 Worker 通过条件更新排他领取；租约到期后允许接手。旧 Worker 可能仍在运行，因此写回时还要检查执行代次，拒绝失效执行者。等待审批期间不保留长事务或资源锁，恢复执行前重新检查权限、凭据和资源条件。
5. 处理外部操作的重复执行。首次调用前保存稳定操作 ID，恢复后仍使用它，并由接收端去重或查询原结果。远端成功、本地回执尚未保存时，检查点无法单独判断是否已经发布；无法核对的任务应进入「结果未知、等待核对」，具体边界见[[agent-resume-failure|中断恢复中的重复执行]]。

验证时要真的终止进程并重新启动，分别检查：进入等待后能否恢复、批准后通知丢失能否继续、外部调用成功但回执未保存时是否重复产生效果，以及两个 Worker 竞争时旧执行能否覆盖新状态。以上是设计说明，尚未实现或运行这些验证。
