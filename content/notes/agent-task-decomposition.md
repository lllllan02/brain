**先判断任务能否作为「一项已知操作，或同一种操作的重复」直接完成。** 具体动作已确定、做完能兑现全部要求、途中无需另排决策与阶段，三项都成立，就不必拆分。

任务拆分（Task Decomposition）确定子任务边界；显式计划（Plan）记录依赖、顺序与进度，同一个 Agent 即可执行。

## 什么时候拆？

先让模型写出一份具体的执行说明，回答三个问题：

1. 改哪里、怎么改？必须说出操作对象与做法，例如「把指定文件中的旧域名替换成新域名」。「实现登录」「建设 SSO」只是目标，尚未说明具体操作；还需要选择方案或验证可行性时，这一项不成立。
2. 这些操作做完，是否兑现全部要求？必须列出完成条件，确认没有另一个能力或交付还需要单独实现。代码与对应测试可以共同完成一项修改；认证、会话、应用接入各有行为要实现，不能因为最终只交付一个 SSO 服务就合并算作一项操作。
3. 能否按既定做法做到收尾？普通的读取、修改、测试与修正可以连续执行；若要先试点验收再全量、安排迁移切换与回退，或跨会话分别接续多项未完工作，就需要管理阶段，这一项不成立。

**三项都有事实支持，直接做；任一项明确不成立，先做 Plan；尚缺事实，先查证再判断。** 例如不知道函数位置可以先搜索，不能仅因未读代码就判定需要规划。文件多、操作重复或等待久，本身不触发拆分。

可复制的[[assets/agent-planning-decision.txt|规划判定提示词]]要求模型填写操作、完成条件与推进方式，逐项提供证据。已有计划覆盖的步骤沿用原计划；用户明确要求 Plan 时遵从。

这套默认策略归纳自[[claude-codex-planning-summary|Claude Code 与 Codex 的规划条件]]，以及[[codex-execplans-summary|ExecPlans 的里程碑]]、[[anthropic-long-running-harness-summary|Anthropic 的应用功能清单]]实践。三项判定是自拟策略，来源没有统一的步数或时长阈值；尚未评测模型判定准确率。

## 怎么拆？

从未通过的检查入手：做法未定，先安排探索并得到决定；包含不同成果，分别列出完成条件；存在阶段约束，写清继续推进的条件。然后把工作组织为**「逐步可运行、能够验收的成果」**，按依赖排列。

例如，假设 SSO 的目标是「在应用 A 登录后，访问应用 B 无需再次输入凭据」，可形成以下里程碑。这是拆分示例，不是完整认证架构或安全规范。

| 里程碑 | 完成证据 |
| --- | --- |
| 明确范围和接入约定 | 身份来源、应用接入、过期与退出语义及验收场景有明确约定 |
| 跑通首个应用登录 | 一个应用的登录与身份识别链路可运行、可验证 |
| 接入第二个应用 | A 登录后访问 B，符合约定的免重复登录行为 |
| 补齐边界并整体验收 | 约定的过期、退出、失败场景验证通过，两个应用的组合行为符合目标 |

每项写清输入、产物和验收。仍有不同成果需要分别管理就继续分；已经能写出具体操作、完成条件与推进方式，就停止细分。只细化近期工作，远期保留里程碑；各项完成后仍要整体验收。

前提改变时[[agent-replanning|调整剩余计划]]；跨会话用[[agent-task-state|任务状态]]保存成果与待办。
