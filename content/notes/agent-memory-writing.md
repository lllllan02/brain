**记忆写入是把交互转成有证据、有适用范围、可维护的记录；新信息到来时，还要判断它是在补充、纠正还是描述另一种情况。** 保存全部聊天可以提供证据，但不能替代这层判断。

## 哪些信息值得提取？

假设用户说“这个项目的示例优先用 Go”。模型可提出 `example_language=Go`，同时保留原消息与项目范围。只保存“喜欢 Go”会丢掉“示例”和“这个项目”的限定，后来容易误用。

候选一般来自稳定偏好、重要事实、长期目标和可复用经历。一次工具报错本身不一定值得长期保留；若已经确认原因、修复方法及验证结果，才可能形成“遇到相同条件如何处理”的经验。临时计划可保留，但需要时间边界。

[[codex-memory-pipeline|Codex 的提取提示]]要求区分用户表达、助手提议与实际验证，允许没有可保存内容。由此可采用一个实用判断：这条记录能让未来某类任务少一次重复询问或少走一段已知弯路吗？它的适用范围有证据吗？

## 什么时候写？

| 方式 | 收益 | 代价 |
| --- | --- | --- |
| 主交互中写入 | 明确偏好、纠正可及时生效 | 增加等待与模型调用，不能每次都无差别提取 |
| 阶段或事件触发 | 能结合完整结果整理经验 | 需有可靠触发点，不能假设会话总有正常结束事件 |
| 后台批量处理 | 减少主流程延迟，便于跨交互整合 | 新旧会话可能短暂看到不同状态，需要排队、重试和完成确认 |

[[langgraph-memory|LangMem]]提供主交互与后台两种方式；Codex 展示后台提取再整合的实现。应用可让明确纠正先同步生效，经验提炼后台完成；同步“候选已入队”不等于同步“记忆已更新”。

## 新旧信息怎样比较？

先按范围、实体与属性定位，再做语义判断：

| 关系 | 本文建议的操作 |
| --- | --- |
| 没有旧值 | 新增，保存来源与时间 |
| 同一内容重复出现 | 保留原条目，必要时补证据，不无限增加副本 |
| 同一范围内明确纠正 | 替换当前值，按需求保留历史与替代关系 |
| 内容互补 | 合并时保留条件，避免摘要把例外抹掉 |
| 范围不同 | 分开保存，例如项目 A 用 Go，项目 B 用 Python |
| 证据矛盾或范围不明 | 保留待确认状态，不能仅凭新消息更晚就覆盖 |

这是一组应用策略，不代表所有记忆产品自动提供。[[mem0-paper-memory|Mem0 论文]]通过相近旧记忆辅助模型选择新增、更新、删除或不变；[[mem0-memory|当前 Mem0 文档]]则将 add 定义为追加式写入，纠正使用显式 update。论文机制与目标版本 API 应分别核对。[[graphiti-memory|Graphiti]]又采用时间关系维护当前与历史事实，不能把这些语义视为相同。

## 模型提出改动后，程序还要做什么？

模型可以生成结构化候选和建议动作。程序从可信会话绑定用户、项目，检查来源消息是否存在、字段与操作是否合法，再读取当前版本并提交。来源存在不代表语义判断正确，候选是否得到原话支持仍需提取评测或必要的人工核实。两个会话同时修改同一条时，基于旧版本的写入应失败或重新比较，避免后完成的旧任务覆盖新纠正。

后台任务还应以来源 ID／任务 ID 防止重复消费，并区分“无需保存”与“处理失败”；只有后者需要重试。涉及多个主记录和索引时，要明确事务或最终一致性策略。记录写入成功后，才进入后续的检索与维护流程。

## 用户刚纠正偏好，后台提取为什么又把旧值写回来？

旧会话提取任务读到“项目用 Python”，尚未完成；用户随后明确改用 Go。旧任务晚到时若直接覆盖，就会把已经纠正的内容恢复。按任务完成时间排序，反而把旧信息当成最新信息。

候选写入应带上来源事件与所依据的记录版本，由程序核对当前状态；冲突时读取新值重新判断，不进行无条件覆盖。显式纠正可以及时生效，异步提取再补充来源与关系。新消息是临时例外还是长期变更，也应结合适用项目与用户表达判断。

重复处理同一来源需避免重复创建，但“没有值得记住的内容”与“提取服务失败”要分开记录。前者可以完成任务，后者需要可控恢复；把两者都返回空列表，会让记忆缺失无法排查。
