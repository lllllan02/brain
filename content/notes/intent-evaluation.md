**意图识别上线前，要同时验证分类、回退、参数与最终路由；上线后还要检查延迟、成本和真实请求的变化。** 总体准确率高，可能只是查询类占多数，掩盖了少量「只查询却进入提交」的错误。

## 测试集怎样准备？

先从脱敏的真实会话和人工标注开始。为每条记录保留当前消息、必要上下文、当前状态、期望任务和字段，以及允许的下一步。下面是自拟用例格式，不是某个平台协议：

```json
{"id":"case-01","state":{"order_id":"A"},"text":"先别退，只查能不能退","expected":{"intent":"refund_eligibility","order_id":"A","next":"check_eligibility","forbidden":["submit_refund"]}}
```

训练集学参数，验证集选提示、模型和阈值，最终测试集检查选定方案。按会话、重复模板或时间分组，避免同一句改个订单号就分别进入训练和测试。真实分布的样本用于估计整体效果，专门收集的否定、域外、条件和高风险误操作用例用于检查边界；两类结果分开报告。

含混输入可以标为「应澄清」，多目标请求可以标记所需目标集合或当前实现应回退；不要强行给所有句子一个业务标签。标注者不一致时先复查类别定义和上下文。[[rasa-nlu-data-practice|Rasa 数据实践]]强调版本管理，[[intent-production-testing|Lex 的测试建议]]还要求测试字段与当前 Bot 定义一致。

## 看哪些指标才能决定改什么？

| 指标 | 计算口径 | 用途 |
| --- | --- | --- |
| 各类别 precision / recall | 正确预测为该类 / 所有预测为该类；正确预测为该类 / 所有真实该类 | 查误路由与漏识别，不能只汇总大类 |
| Macro-F1 | 各类别 F1 的算术平均 | 观察小类，不让大类数量完全支配结果 |
| 接受率 | 未回退的请求数 / 全部测试请求数 | 看自动处理覆盖范围 |
| 接受后错误率 | 已接受但类别错误数 / 已接受请求数 | 与接受率一起判断阈值取舍 |
| 域外误接受率 | 域外但被接受为业务任务数 / 全部域外请求数 | 检查未知需求是否被硬分配 |
| 槽位与会话成功率 | 正确字段 / 所需字段；所有关键状态和动作均正确的会话 / 总会话 | 检查分类后是否真正完成任务 |

分母为零时应记为不适用，不能记成零错误。槽位先约定归一化和比较方式；订单号 A 与 B 不允许模糊匹配。[[azure-clu-intent-design|CLU 的评估口径]]可帮助区分类别和实体指标，[[intent-production-testing|Lex 的逐轮报告]]则说明为何还需单独测整段会话。

## 阈值怎样选择，而不是凭感觉设 0.8？

固定模型后，在验证集保存最高分标签、最高分及第二名分数。扫描候选阈值和分差，观察覆盖与错误；选择规则前先约定业务能接受的错误成本，再用未参与选择的测试集验收。不能只提高阈值直到剩下一两条请求都正确。

下面的 Python 3 标准库示例保存为 `thresholds.py` 后运行 `python thresholds.py`。五条分数为自拟教学数据，用于展示分母和取舍，不是模型实测结果；只演示最高分阈值，未实现分差或按类别阈值。

```python
# (真实标签, 最高分标签, 最高分)
rows = [
    ("query", "query", 0.95),
    ("submit", "submit", 0.82),
    ("query", "submit", 0.91),  # 高分也会错
    ("unsupported", "query", 0.65),
    ("query", "query", 0.55),
]
for threshold in (0.50, 0.80, 0.95):
    accepted = [r for r in rows if r[2] >= threshold]
    errors = sum(truth != predicted for truth, predicted, _ in accepted)
    error_rate = errors / len(accepted) if accepted else None
    print(threshold, "coverage=", len(accepted) / len(rows),
          "accepted_error=", error_rate)
```

本地运行得到：阈值 0.50 接受率 100%、接受后错误率 40%；0.80 为 60%、约 33.3%；0.95 为 20%、0%。最后一个配置只接受一条样本，不能据此宣称可上线。真实验证还要计入错误的严重程度和样本量；分数与错误的关系可能因类别不同而不同。

## 模型版本怎样发布和回滚？

以下是结合[[intent-production-testing|维护方测试流程]]归纳的自建服务发布方案，并非已经部署的系统：

1. 固定版本：记录类别定义、训练数据或提示、模型、Schema、规则及阈值，保留可回滚产物。
2. 离线回放：比较同一批单句与多轮用例；查询误触发提交、用户撤回后仍执行等关键反例不通过就继续修正。
3. 影子验证：新版本读取实际请求副本并记录决策，不执行退款等副作用；与现有结果及人工标注比较。
4. 小流量发布：按会话固定版本，观察误路由、回退、转人工、任务完成、P95 延迟和每次成本。退化时回滚识别配置；已执行的业务操作不能靠回滚模型撤销。

生产问题先定位层次：分类对但调用错接口，修路由映射；对象 A 被换成 B 后仍用旧资格，修状态；整体低分且新说法增多，检查数据变化；只在某个新版本退化，比较配置和样本差异。日志至少能关联请求、会话、识别版本、候选、回退原因、所选流程与真实执行结果，并按隐私要求控制原文保存。

这些检查也构成技术设计讨论的主线：用什么数据证明方案可用，阈值换来了什么，失败怎么恢复，版本怎样退出。不能以一次演示或供应商宣传数字代替本业务评测。代码仅验证指标计算，未验证真实流量上的质量或性能。
