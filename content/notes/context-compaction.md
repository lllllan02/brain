**上下文压缩（Context Compaction）是将部分历史提炼成较短摘要，与保留的原始消息共同构成后续输入的机制。** 对话和工具结果不断增长，有限窗口无法一直容纳完整历史。相比直接[[context-trimming|裁剪]]，压缩能延续旧历史中的目标、进度与关键结论，但会损失部分细节。

## 哪些内容压缩，哪些保留？

[[context-budget|上下文预算]]决定何时需要缩减输入。下面以连续前缀压缩为例：模型总结较早历史，程序保留边界之后的原始消息。

![[assets/context-compaction-process.png|旧历史生成摘要，边界后的原始消息保留，再继续 Agent Loop]]

**「保留边界由程序按策略划定，不默认交给模型自由选择。」** [[pi-compaction-summary|Pi]]按近期 Token 预算确定范围，消息条数不固定；[[claude-compaction-summary|Claude 的近期保留示例]]由应用指定轮数。图中的三条保留消息只是示例，切分时还要保证工具调用与返回结果完整配对。

连续保留近期消息容易实现，但较早的重要交互也可能需要原样保留。选择性保留可以覆盖这种情况，不过需要额外的消息选择与依赖校验，不能视为图中方案的默认能力。**「保留哪些原文」与「摘要写多细」是两个独立问题。**

## 压缩后得到什么？

模型根据[[context-compaction-prompt|摘要提示词]]提炼目标、约束、关键事实、进度与待办；程序负责把摘要和保留原文组织成有效输入，保留消息中的调用 ID 与返回内容不从摘要重新生成。

**「摘要」只是压缩结果的一部分，最终供模型使用的仍是一组消息。** 例如 [[langmem-summarization-summary|LangMem]]的摘要模型返回文本，框架再组装消息列表；服务端接口也可能返回须完整回传的专用压缩块，不能一律当作 Markdown 处理。

要跨轮次复用，还需记录摘要覆盖了哪些历史，避免重复带入或遗漏；具体的保存格式、位置与读取组合由[[context-compaction-storage|压缩摘要的存储与读取]]展开。

## 怎样看待信息损失？

摘要可能遗漏后续才发现有用的细节，因此应区分「不再放进窗口」与「删除原始历史」。原文仍可访问时，可以[[context-loading|按需回查]]；没有可用原文时，可能需要重新执行工具，增加成本，结果也未必相同。带副作用的操作不能仅为找回结果而盲目重做。

压缩是否有效，要看 Agent 能否准确延续任务，以及节省的资源是否超过总结和回查的开销；[[context-compaction-evaluation|效果评估]]据此检查信息保留、任务表现与总成本，不能只看摘要缩短了多少。

## 压缩后对话很流畅，为什么任务反而做错了？

摘要把“用户只允许查询，是否提交尚未确认”压成“正在处理退款”，读起来通顺，却把关键执行边界丢掉了。语言连贯与任务可接续是不同要求。

压缩应优先保留当前目标、禁止事项、已证实事实、未解决问题和下一步依赖，区分已执行与仅计划。金额、对象、错误码和证据位置等影响动作的细节不能只保留模糊概括。可重取的大日志则保存定位信息，避免摘要重复承载全部细节。

多次压缩还会放大早期误差。重要状态由结构化记录或原始证据核对，不只从旧摘要继续推导；后续出现冲突时回查来源。是否值得压缩，要比较实际续做表现和总成本，不能只以压缩率评价。
