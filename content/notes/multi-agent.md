**多 Agent 协作是让多个具有各自任务、上下文或能力配置的 Agent，通过委派、交接或消息交换共同完成目标的组织方式。** 它可以分散上下文负担、并行探索和复用独立能力，也引入通信、协调与验收成本。

例如，研究一个产品时，市场、技术与使用反馈可以分别调查，再合并证据；如果每一步都依赖上一轮完整讨论，拆分反而需要反复传递信息。**「能否形成有界、可验收的分工」**比角色名称或 Agent 数量更能决定收益。

## 先区分两个选择层次

协作组织回答「谁分配任务、谁决定下一步、结果交给谁」；通信接口回答「这些参与者怎样交换请求、状态与产物」。两层可以组合：主 Agent 在内部创建子 Agent，也可以把某项工作委派给实现 A2A 的远端服务。

一个模型可支撑多个 Agent，同一个 Agent 也可按需切换模型。给一次对话写上多个角色、并发执行几个固定函数，都不足以说明已经存在多个独立 Agent 运行。[[agent-vs-workflow|工作流]]还可以在外层按固定步骤编排多个 Agent。

## 常见分工方式怎么选？

下表按控制流归纳，主要依据 [[langchain-multi-agent|LangChain 的模式划分]]，补充群聊与共享任务方式；这些模式并非互斥产品。

| 方式 | 控制与结果如何流转 | 适合的条件 | 主要代价 |
| --- | --- | --- | --- |
| 路由（Router） | 分类后交给一个或多个专家，必要时汇总 | **「类别清楚」**，不同请求需要不同能力 | **「误路由」**会让后续处理从错误前提开始 |
| 主从委派（Supervisor / Orchestrator-workers） | 主 Agent 分解与调度，子 Agent 交回结果 | 任务可拆，且需要**「统一汇总」** | 主 Agent 可能成为瓶颈，分工不清会重复工作 |
| 交接（Handoff） | 当前处理者将后续控制权转给另一处理者 | 专家需要接续多轮对话或不同阶段能力 | 需传递必要历史，防止反复转交、遗漏责任 |
| 并行分发与汇总（Fan-out / Fan-in） | 多个独立分支同时推进，按规则收集结果 | **「独立探索」**、批量研究、不同角度审查 | 慢分支、重复调查与汇总开销；可嵌入主从或固定工作流 |
| 群聊／轮流讨论（Group chat） | 按轮次选发言者，向成员共享消息 | 需要回应彼此证据、讨论候选方案 | **「讨论变长」**、信息噪声和停止条件问题；不必并发 |
| 共享任务／黑板（Shared task board / Blackboard） | 成员读取共享任务与产物，认领或发布结果 | 有持续协作、依赖更新和成员间沟通需求 | 需处理归属、重复认领、过期状态与写冲突 |
| 生成—评审—修改 | 生成者交付，评审者反馈，必要时迭代 | 评价标准明确，反馈能帮助改善 | 额外调用可能只是重复确认，评审本身也会出错 |

这里的黑板泛指通过共享状态协调的架构，不是统一协议。[[autogen-group-chat|AutoGen 的群聊]]展示按共享历史选择下一位发言者；[[claude-code-agent-collaboration|Claude Code 的团队机制]]展示独立会话、任务列表与成员消息。两者对参与方式与状态组织的选择不同。

生成与评审可以只是两次模型调用；当双方各自运行工具循环时，才进一步形成多 Agent 实现。独立评审或多方辩论能增加检查角度，**「达成共识不能代替证据与验收」**。

## 子 Agent 和 A2A 分别解决什么？

[[agent-subagents|子 Agent（Subagent）]]接收有界子任务，运行自己的循环，再向调用方返回成果。创建过程涉及能力配置、上下文组装、执行实例与生命周期管理；它可以串行执行，也可以后台运行。

[[a2a|A2A（Agent2Agent 协议）]]用于独立 Agent 服务之间的能力发现、任务交互和产物交换。它不负责替业务决定怎么拆任务，也不等于远程创建一个受自己完全控制的子 Agent。

小型应用内部可以直接调用函数、SDK 或图节点；自有服务间也可约定 HTTP API 或消息队列。需要跨框架、跨团队复用服务时，A2A 的共同语义更有价值。[[mcp|MCP]]提供工具和资源接入，远端 Agent 内部也可以使用 MCP；选择应看接口承担的职责。

## 上下文分开以后，怎样保持任务一致？

多个窗口不会自动同步目标、记忆或文件状态。以下是结合上述实现与 [[anthropic-multi-agent-research|Anthropic 研究系统经验]]形成的设计建议：

- 给每个分支明确输入、负责范围、交付物与停止条件；主任务保留最终验收责任。
- 将必要约束与资料引用传给分支，完整产物保存在可追溯位置，摘要不能丢掉证据和未解决问题。
- 并行读取通常容易安排；共享修改应明确写入归属、版本与合并规则，必要时串行化冲突部分。
- 区分等待依赖、失败、取消和完成；为整体设置预算，并决定缺少某个结果时能否交付部分成果。
- 每次工具执行仍检查权限。子 Agent 的文字请求、远端报告或共享记录不能替代用户授权。

[[agent-task-state|任务状态]]记录谁负责什么，[[agent-checkpoint-recovery|检查点与恢复]]记录进展和外部操作结果。共享数据库、文件目录或记忆服务只是存储选择，不会自动解决一致性与冲突。

## 怎样判断协作值得？

先比较单 Agent、单 Agent 配合按需加载，以及多 Agent 在同一批任务上的结果。按 [[agent-evaluation|Agent 评测]]同时看质量、总 Token、工具调用、端到端延迟与人工接管；再做同预算比较，区分协作结构的收益与单纯增加计算的收益。

[[mast-multi-agent-failures|MAST 失败研究]]提示同时检查分工设计、成员间失配和任务验证。Trace 应能关联主任务、分支、消息与最终产物，让错误可定位到「没分派」「没传到」「执行错」还是「没验收」。

需要不同工具或大量独立资料时，先尝试有界子任务；主要是专业指令不同，优先考虑按需加载；外部团队已提供独立服务时，再评估 A2A。任务强依赖、持续共享上下文或共同修改同一对象时，先保留单 Agent 或明确工作流，只有实际评测支持时再增加协作层次。
