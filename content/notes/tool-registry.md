**工具注册中心是统一保存工具定义与执行入口、支持注册和查找的组件。** 执行器按名称取得工具，模型可见的工具定义也从这里生成；它可以只是进程内的注册表，不必是独立服务。

把名称、用途、参数结构和执行入口集中管理，可以避免工具增多后不断扩充调用处的分支，并统一处理启用状态和权限信息。执行时仍需校验参数与权限，注册不代表获准调用。

程序先获得工具定义与执行入口，再加入注册表：来源可以是开发者写好的工具、用户配置的 API，或通过 [[mcp-flow|MCP 接入流程]]发现的外部工具。发现解决「有哪些工具」，注册保存「如何找到并执行它们」。

## 最小实现

一种实现示例是「统一接口 + Map」：工具接口提供名称、Schema 和执行方法，用 `map[string]Tool` 保存实例，提供 `Register`、`Get`、`List` 方法。执行器按名称查找，再调用统一执行接口；注册时检查重名和定义有效性。

工具来源增多时，可以按来源封装工具集，再组合、加前缀或重命名；每轮筛选可见定义，调用时仍回到对应执行入口。[[pydantic-toolsets-summary|Pydantic AI 的 Toolsets]]提供这种实现参考：用 `get_tools()` 与 `call_tool()` 分别组织定义与执行。工具集是应用内抽象，不等于独立注册服务。

## 静态与动态注册

- 静态注册：工具由开发者预先实现，在启动时注册；集合相对固定，新增实现通常需要修改代码并部署。
- 动态注册：运行期间发现、加入、更新或移除工具，例如新增 MCP Server 的工具，或允许用户配置 API 工具。

动态注册不等于生成工具代码。已注册工具的定义何时进入模型上下文，由[[tool-loading|工具按需加载]]等策略决定。用户自定义工具还需检查定义、权限与执行隔离，这些属于[[tool-calling-harness|工具调用的 Harness 能力]]。
