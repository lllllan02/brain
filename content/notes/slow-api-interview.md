> 生产实践见：[[slow-api-investigation|接口变慢排查]]。

**回答要点：先定位是哪一段慢，再定位那一段为什么慢；用指标缩小范围，最后止损并验证。** 不要一上来就猜代码或加机器。

可以按这四步展开：

1. **确认现象、划定范围**：看延迟分位数（P50/P95/P99）、错误率、QPS、超时率，按接口、实例、机房、用户切分，区分是全站变慢、单接口变慢还是长尾；确认起始时间，和发布、扩容、依赖变更对齐。
2. **分段定位耗时**：用 [[opentelemetry|链路追踪]]、日志或埋点，把端到端拆成排队/连接、应用内计算、下游 RPC、数据库几段，看大头在哪一段；注意父 Span 含子调用，不能把嵌套耗时相加。
3. **针对该段找原因**：应用内查 CPU、GC、锁、线程池；依赖查慢 SQL、[[db-connection-pool|连接池排队]]、下游超时与重试；入口查带宽和队列。
4. **止损并验证**：先限流、降级、回滚或隔离故障依赖，保留现场；修复后用同类流量对比延迟、吞吐、错误率，确认真的恢复。

常见追问与加分点：

- 为什么看 P99 而不是平均延迟；
- trace 上最大的 Span 不一定是要点（父含子、并行分支的关键路径不等于各分支之和）；
- 时间重合不等于因果，发布后变慢不一定是发布导致；
- 高频元凶：慢 SQL 或缺索引、连接池排队、缓存失效、重试放大、GC 停顿、下游超时。
