为什么不直接用 HTTP 请求，而要设计 RPC？本地方法调用很自然——有类型、有返回值、异常直接抛；服务拆开、跨进程后，调用只能走网络。手写 HTTP 也能通，只是每个调用点都要拼 URL、序列化参数、解析响应、处理超时和错误；内部调用频繁、数据对象大时，文本协议和反复建连还会拖慢速度。RPC 要解决的就是：让跨进程调用在体验上像本地调用，同时补齐网络特有的效率和可靠性——**它的本质仍是一次网络请求**。

顺着这些痛点，设计点一个个长出来：

- **想「像本地调用」**：客户端要有桩（stub，动态代理或代码生成），把「方法名 + 参数」编码成消息、把结果还原成返回值；服务名、方法、参数和版本用 IDL 之类的契约约定，双方才能对齐。
- **想比手写 HTTP 省**：序列化（serialization）选二进制（Protobuf 等）减少体积和解析成本，连接复用、多路复用减少建连与阻塞。注意 gRPC 就是 HTTP/2 + Protobuf——RPC 不等于必须绕开 HTTP。
- **实例会变**：扩缩容、发布让地址不再固定，所以需要 [[service-discovery|服务发现]]和客户端负载均衡，而不是写死 IP。
- **网络会慢会断**：本地调用不会失败，远程会。每次调用要带截止时间（调用预算），失败要区分连接失败、超时和业务错误，供重试与 [[circuit-breaker-design|熔断]]判断；连接断开只说明没收到确定结果。
- **重试要安全**：写操作重试可能重复生效，所以要 [[idempotency|业务幂等键]]并由服务端保存执行状态；只在客户端去重挡不住远端重复扣款。
- **出问题要能查**：跨进程看不到调用栈，所以要记录方法、实例、耗时和状态，并串起 [[opentelemetry|追踪上下文]]。
