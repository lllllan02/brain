**混合检索同时使用词项与语义等检索信号，再把候选合为一个列表。** 它适合问题既含精确对象又有自然语言描述的情况，例如“错误 E104 导致登录反复跳转”，其中编号与现象都可能有用。

## 为什么不直接相加分数？

BM25 和向量分数的尺度、分布不同，换模型或语料后也可能变化。直接相加会让数值范围大的那路主导；若采用加权分数，必须先验证归一化与权重。

RRF（Reciprocal Rank Fusion，倒数排名融合）使用排名：每路对文档贡献 `1 / (c + rank)`，跨路求和，再按和排序。c 为平滑常数，rank 从 1 起；未出现在某路的候选，该路贡献为 0。[[rag-retrieval-ranking|Azure 的融合说明]]明确区分 c 与近邻返回条数。

假设词项结果为 A、B，向量结果为 B、C，示例取 c=60。A 和 C 各获一项贡献，B 得到 `1/62 + 1/61`，因此融合后 B 靠前。这只是手算机制示例，不表示 c=60 适合所有业务。

## 融合为什么仍会错？

两路可能都偏爱同一批重复内容，或漏掉只有一个关键词匹配的关键例外。RRF 不读取正文，不知道文档是否真的支持结论；它也不保留原始分数之间“相差很大”的信息。

工程上先按稳定 chunk ID 去重并保留各路排名，统一身份和版本过滤；片段内容相近但条件不同，不能仅凭相似就删除。需要更细判断时再做重排。

固定候选预算比较纯关键词、纯向量和融合结果，观察不同问题类型的必要证据覆盖、延迟与后续成本。多路结果增加了什么证据，比“混合分数更高”更能说明价值。
