**经验记忆保存任务条件、采取的行动和实际结果；技能复用进一步把已验证的方法组织为可重复使用的步骤或程序。** 前者帮助判断过去发生了什么，后者减少相似任务中的重复探索。

## 从经历到做法，中间缺什么？

假设 Agent 为项目甲运行测试，直接在根目录执行失败，进入 `apps/api` 后成功。只记「测试失败过」无法指导下一次；记「所有项目必须进 apps/api」又扩大了范围。

更有用的经验是：「项目甲的测试入口位于 apps/api；根目录没有对应脚本；在该目录执行指定命令通过。」它保留环境、失败原因和验证依据。若需要复用为工作步骤，则先读取项目配置、定位测试入口，再执行并检查退出状态，而不是硬编码一次经历的路径。

这里的[[agent-self-correction|反思与自我纠正]]负责找出并修复当前问题；记忆决定哪些结果值得跨任务保存，二者可以配合。

## 可以保存哪种形态？

| 形态 | 怎样复用 | 收益与代价 |
| --- | --- | --- |
| 经历片段 | 召回相近任务，比较条件与结果 | **「保留具体证据」**；每次仍需解释和适配 |
| 条件化经验 | 读取失败原因、适用条件与建议 | **「减少重复试错」**；错误归因会反复误导 |
| 步骤或程序 | 检查前提后调用、组合 | **「减少重复生成」**；需维护依赖、输入契约和回归 |

[[reflexion-summary|Reflexion]]把尝试反馈转为文字经验，影响后续尝试；[[voyager-skill-memory|Voyager]]把通过成功检查的程序加入技能库，供新任务检索和组合。两者说明跨运行改进可以来自外部记录，不必通过修改模型参数实现。

## 怎样形成可采用的经验？

模型根据轨迹和反馈提出原因与建议；程序附上实际结果、环境及来源，区分「尝试过」「单次验证成功」与「已有适用范围内的回归证据」。当时成功与因果解释正确是两回事，不能把模型自评直接当作验证。

新任务召回经验后，先比较项目、依赖版本、输入前提和权限，再决定是否复用。记忆可提示应查什么，却不能替代对当前文件或环境的核对。可执行程序还需通过现有工具权限检查，不能因为来自技能库就自动运行。

## 怎样知道它确实帮助了后续任务？

让两组 Agent 处理相同的新任务，一组不读经验，另一组读取候选经验，比较成功率、重复错误、调用成本和不适用经验的误用。测试集应包含「表面相似但条件不同」的任务；只在原题上反复尝试，不能证明已经获得跨任务能力。

若只有一次局部成功，就保存为有范围的经历；当方法的输入、检查点与适用条件足够明确时，再组织为步骤或技能。升级依据是可解释和可验证的做法，而非记忆条目的数量。
