**ReAct 组织逐步决策，Plan-and-Execute 分开整体规划与单步执行，Replanning 调整剩余计划；三者可以组合。**

任务规划（Planning）是根据目标拆解任务、安排步骤的能力。

[[agent-loop|Agent Loop]] 提供模型决策、工具执行与结果反馈的循环。任务变长后，只关注下一步可能遗漏整体目标；先列出计划，又可能遇到新证据使后续安排失效。规划与执行模式需要同时考虑「怎样安排任务」和「怎样利用反馈继续推进」。

## 这些概念分别解决什么问题？

| 概念 | 关注的问题 | 主要特点与代价 |
| --- | --- | --- |
| [[react-agent\|ReAct（推理与行动交替）]] | 根据当前信息，接下来做什么？ | 推理、行动与观察交替，能**「及时利用反馈」**；多轮判断增加开销，也可能**「重复行动」** |
| [[plan-and-execute\|Plan-and-Execute（先规划再执行）]] | 整体有哪些步骤，每一步怎样落实？ | **「分开整体规划与单步执行」**，便于检查目标覆盖；**「初始计划可能失效」**，规划也有调用成本 |
| [[agent-replanning\|Replanning（重新规划）]] | 剩余步骤、顺序或策略是否需要改变？ | **「根据新证据调整计划」**；**「频繁检查和修改有成本」**，仍需验证新计划 |

ReAct 也能在行动中形成或修改计划；Plan-and-Execute 也可在执行后接入重规划。是否显式规划、何时检查计划，需要由程序规则或模型决策确定，不会仅因任务复杂而自动切换。

## 三者怎样配合？

一种组合是：**制定整体计划 → 用 ReAct 完成当前步骤 → 检查剩余计划 → 继续执行或结束**。规划器生成步骤，执行器围绕当前子目标决定具体行动，程序执行工具并回传结果。一个计划步骤可以包含多轮行动，不能将它等同于一次工具调用。

查询成功得到的证据仍可保留，但「数据库正常、应用 CPU 异常」使原先检查索引的方向不再适用，因此需要修改剩余工作。工具调用成功，也可能需要改变计划；改计划不会自动撤销已执行的操作。

**「检查不等于每次都改计划。」** 程序可在计划步骤交界处、固定行动间隔或执行出错等事件发生时发起检查；模型结合目标、计划和证据判断是否需要调整。仍可继续原计划，也可按[[agent-feedback-mechanisms|反馈与调整机制]]处理暂时故障或局部错误；只修正参数或答案，通常不涉及重新规划。具体检查入口、计划更新和停止条件由 [[agent-replanning|Replanning]] 展开。

## 怎样取舍？

下一步高度依赖刚获得的信息时，可以采用逐步交互；任务已有可识别的阶段、容易遗漏整体目标时，可以考虑显式规划。执行中信息变化明显时，再配置合适的计划检查规则。应比较任务完成情况、总耗时和费用，不能仅凭生成了计划判断效果更好；预算耗尽也不等于任务完成。

计划粒度还会影响执行方式：子目标需要执行器继续决定具体行动；带工具参数和依赖的计划可以交给程序调度。若主要开销来自独立工具调用相互等待，应检查[[tool-scheduling|工具执行调度]]；[[llmcompiler-summary|LLMCompiler]]展示了按依赖派发任务的方案。先规划并不自动带来并行、更快或更低成本。
