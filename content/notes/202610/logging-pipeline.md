日志系统需要完成生成、采集、缓冲、解析、存储和查询。先确定查询方式与允许丢失程度，再选择组件，避免把所有日志都送进成本最高的检索系统。

应用优先输出结构化字段，例如时间、级别、服务、事件名和 trace_id。错误堆栈应保留完整边界，多行采集规则需要与输出格式配合；敏感信息尽量在源头去除。[[opentelemetry|追踪上下文]] 可以把日志与一次具体请求关联。

采集器需要记录读取位置，并处理文件轮转、进程重启和发送失败。有本地队列不等于永不丢数据：队列容量、磁盘故障、文件提前清理和确认时机共同决定恢复边界。Kafka 等缓冲层适合解耦吞吐与重放，但会增加一套需要运维的系统。

| 查询需求 | 可评估的存储方向 |
| --- | --- |
| 任意字段检索和全文搜索 | [[elk\|ELK]] / Elasticsearch |
| 已知服务与时间范围内筛选日志 | [[loki\|Loki]] |
| 大规模结构化聚合分析 | [[clickhouse\|ClickHouse]] |
| 长期低频留存 | 对象存储与按需查询 |

诊断日志与业务事实事件应分开定义可靠性。调试日志可以采样，支付成功事件却不能因日志队列满就静默丢弃。日志里出现一行“发送成功”，也不能替代交易系统的持久状态。

保留周期、冷热分层、索引字段和租户配额共同影响成本。查询需要明确时间范围，写入链路则监控丢弃数、队列积压、解析失败和端到端延迟。
