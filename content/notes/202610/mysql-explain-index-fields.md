# MySQL EXPLAIN 索引相关字段

`possible_keys / key / key_len` 分别回答**有哪些候选索引、计划选了哪个、使用了多长的索引键**。把三者与查询条件和索引定义一起看，才能判断索引怎样参与访问。

1. **possible_keys：候选索引**。根据条件和现有索引结构，列出可能用于查找数据的索引。候选不代表最终一定使用，也不代表按当前连接顺序都可使用。
2. **key：计划选中的索引**。例如候选为 `idx_user_id,idx_status`，而 key 为 `idx_user_id`，说明选择了前者。`key=NULL` 表示这一步没有选用索引。候选存在但未选时，应结合访问比例、回表成本和统计信息分析。
3. **key_len：使用的键长度，单位字节**。结合类型、字符集、是否可空和索引定义，辅助判断联合索引用了哪些键列，不能直接把它当成字段个数，也不是越大越好。

例如普通联合索引 `idx_ab(a,b)`，a、b 均为 `INT NOT NULL`：按 `a=1` 查找时 key_len 常见为 4，按 `a=1 AND b=2` 查找时常见为 8。这是限定表结构下的示例；可空列、变长字符串等会改变长度。

**用于定位的键列，与索引能提供的全部作用不同。** 后续列还可能用于索引条件下推、覆盖或排序，不能仅凭 key_len 判断它们完全没用。

`possible_keys=NULL` 也可能出现非空 key：没有适合条件定位的候选索引时，优化器仍可能选择覆盖查询的全索引扫描。反过来，key 非空只说明选了索引，仍需看 [[mysql-explain-type|type 是否为 index]]、预计读多少行。
