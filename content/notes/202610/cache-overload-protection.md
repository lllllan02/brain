这三类问题的共同结果是大量请求绕过缓存进入后端，但触发原因不同，应针对不存在的数据、单个热点和大面积失效分别处理。

| 问题 | 触发条件 | 主要措施 |
| --- | --- | --- |
| 穿透 | 反复查询不存在的数据 | 参数与权限校验、短时空值缓存、布隆过滤器 |
| 击穿 | 热点 key 到期或未加载 | [[go-singleflight\|请求合并]]、受控重建、允许时使用旧值 |
| 雪崩 | 大量 key 同时失效或缓存整体不可用 | TTL 抖动、分批预热、后端限流与降级 |

[[bloom-filter|布隆过滤器]]可能误判「存在」，因此仍需查后端；在过滤器构建完整且更新正确的前提下，它不会把已经加入集合的元素判为不存在。新数据未及时加入过滤器，会造成应用层的错误拦截，不能只引用算法性质而忽略维护过程。

诊断时看 key 是否实际存在、是否集中在一个热点，以及缓存服务是否整体异常；故障持续时间不是分类依据。不存在的数据可能被空值缓存挡住，热点重建也可能因为反复失败持续很久。

热点重建可让同一 key 只有一个请求回源，其余等待有限时间或读取允许的旧值。锁等待必须有上限，重建失败也需退避，否则锁超时后可能出现新一轮同时回源。

采用逻辑过期可以保留旧值，并由受控任务异步刷新，但它把等待转化为陈旧数据风险。应定义最长可接受陈旧时间、刷新失败后的行为和首次没有旧值时的回源策略。

缓存整体故障时，不能无条件把全部流量转给数据库。应根据后端容量执行 [[rate-limiting|限流]] 与 [[circuit-breaker-fallback|降级]]，优先保留关键业务。降级数据的有效期和可接受误差需明确，不能把旧库存作为成交依据。

恢复阶段也需要控制预热速度。一次性加载所有 key 会让数据库、网络和 Redis 同时承压，可能在故障刚恢复时制造第二轮故障。
