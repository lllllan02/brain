一致性哈希把节点与 key 映射到同一哈希环，通常让 key 归属顺时针遇到的第一个节点。增删节点只改变相邻区间的归属，从而避免直接修改 `hash(key) % 节点数` 带来的大范围重映射。

在节点和 key 足够均匀的理想条件下，从 N 个节点增加一个节点，新节点平均承接约 `1/(N+1)` 的 key；移除一个节点平均影响约 `1/N`。这是映射分布的期望，不是每次扩容的实测迁移比例，也不保证每个节点负载相等。

虚拟节点让一台物理机器在环上占据多个位置，通常能改善分布，并可按机器容量分配不同数量的位置。但一个特别热的 key 仍会集中落到其负责节点，虚拟节点无法自动拆开这个热点。

客户端和服务端还需要一致的成员视图、故障判定与迁移安排。改变路由不会自动把旧数据搬到新节点；迁移期间的读写、旧值回填与重复请求都需要额外处理。

固定槽位是另一种间接映射：先把 key 映射到槽，再维护槽到节点的关系。[[redis-high-availability|Redis Cluster]] 使用固定 16384 个槽与 CRC16 取模，不是直接把节点放到上述哈希环上。两种方式都把「数据归哪组」与「哪台机器负责」部分解耦，但具体算法不同。

用于数据库时，还要结合 [[database-sharding|查询路由与迁移成本]]；用于缓存时，则要为迁移造成的集中未命中预留后端容量。
