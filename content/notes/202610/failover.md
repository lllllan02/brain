故障切换需要把服务职责交给可接替的节点，同时约束旧节点继续工作的能力。心跳超时只能说明当前观察者联系不到目标，不能证明目标已经停止。

通常先通过多个观察或协议规则判断是否需要切换，再选择数据进度满足要求的候选者，建立新的任期或所有权，更新流量入口，并检查客户端恢复。[[redis-high-availability|Redis]] 和 [[raft|Raft]] 的选取与提交规则不同，不能把所有自动切换都当作同一种保证。

网络分区时，新旧两侧都自认为有权写入，就可能发生脑裂。多数派能约束参与共识的成员，但旧客户端仍可能向数据库、文件或外部 API 写入。需要 [[distributed-locks|fencing token 或资源侧校验]]，让接收端拒绝过期持有者；仅删除注册信息不能让旧进程立即消失。

切换前后的在途请求还可能处于「已执行但响应丢失」的状态。客户端重试需要幂等键、状态查询或业务去重，不能直接把超时当作未执行。数据复制延迟也可能导致新主缺少已确认写入，应在 [[high-availability|RPO 与恢复策略]] 中明确。

旧主恢复后应先验证身份并追赶数据，再决定是否切回；不能因为原机器重新上线就重新放开写入。一次演练应检查数据、请求与流量三个方面，而不只检查主节点名称是否改变。
