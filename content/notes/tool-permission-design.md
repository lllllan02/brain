**权限规则用主体、动作、资源和条件匹配请求，给出允许或拒绝，并为允许的操作附加审批、认证等要求。** 下图展示一套通用设计：规则如何驱动判定，以及请求何时停止、暂停或执行；具体字段与组合策略需按产品实现。

## 匹配依据从哪里来？

本地函数和 MCP 工具可映射到统一业务动作，复用检查。身份、角色与资源归属取自可信系统，模型传入的目标只是待检查对象。[[aws-agentcore-authorization-summary|AWS AgentCore]]展示了身份与参数共同参与求值的方式；其 `resource` 指网关，业务对象放在上下文中，不能直接套用通用字段含义。

## 多条规则怎样组合？

本方案采用**同层授权合并、跨层上限取交集、明确拒绝优先、无允许依据则拒绝**。代表用户执行时，用户权限与 Agent 委托共同限定范围，工具的高权限服务账号不能扩大这一范围。

适用的附加要求须全部满足。批准后重新核验，是因为等待期间权限、目标或记录有效性可能变化。普通批准不覆盖禁止项；额外权限须按明确申请依据，由有权者变更授权后重判。必要信息缺失或核验失败时不放行。

## 授权怎样维护和验证？

**规则、授权关系、临时批准记录分开保存**，由可信管理入口维护，Agent 不能自行扩权。[[openfga-agent-authorization-summary|OpenFGA]]将模型与关系分开：授予或撤销关系不必改模型，模型变更使用新版本。临时批准另需绑定调用范围、有效期和使用状态。

发布前测试允许、拒绝、越界、冲突、过期与审批后重判；撤权时核对其他授权路径与缓存。记录规则版本、判定理由和实际执行结果，验证拒绝确实阻止了调用。

## 判定怎样落实到执行？

检查须覆盖所有执行入口。[[claude-permissions-summary|Claude Agent SDK]]的自动放行路径可能跳过审批回调，因此回调不能充当唯一权限关口。

Shell 的脚本、变量与子进程使工具名或命令前缀不足以代表实际行为。[[claude-code-shell-permissions-summary|Claude Code]]和[[codex-exec-policy-summary|Codex]]展示了命令检查、审批与[[sandbox-execution|受限环境]]的配合；无法可靠识别的行为须按策略审批、拒绝或限制执行，人工批准不证明脚本安全。

规则可先用共享代码与配置实现，需要独立管理复杂策略时再引入策略引擎。
