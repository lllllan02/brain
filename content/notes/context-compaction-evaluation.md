**上下文压缩评估是检查缩减历史后，Agent 是否仍能准确延续任务，以及节省的资源是否超过摘要和信息恢复的代价。** 摘要更短、文字更流畅，都不能单独证明压缩有效。

## 需要测什么？

| 维度 | 检查内容 |
| --- | --- |
| 信息保留 | 目标、约束、关键事实、文件状态、决定与待办是否准确，有无遗漏或编造 |
| 任务延续 | 最终任务是否完成，是否重复失败操作、补读原文或重复调用工具 |
| 总体开销 | 压缩前后完整输入大小，以及整项任务的 Token、费用、耗时和调用次数 |

[[anthropic-context-engineering-summary|Anthropic 的工程实践]]强调先确保重要信息保留，再删除冗余。这提供了调优顺序：先定位影响后续行动的遗漏，再追求更小的上下文，而非先规定必须压到某个比例。

## 怎样发现信息丢失？

可参考[[factory-compression-evaluation-summary|Factory 的问答探针]]，在同一个压缩点，对压缩后的上下文提出四类问题：

- 事实：此前发现了什么错误，具体值是什么？
- 状态：哪些文件已修改，哪些检查实际通过？
- 计划：下一步应做什么，还有什么未完成？
- 依据：为什么采用这个方案，排除了哪些方案？

答案应与原始日志、文件差异和测试结果核对。区分「不知道」「记错了」与「把未完成说成已完成」；关键约束即使只漏一项，也可能比遗漏许多普通细节更严重。

Factory 使用模型裁判评分，属于厂商自评；探针答对只能说明部分信息可恢复。模型评分可辅助筛查，关键事实仍需核验，不能直接当作任务成功率。

## 怎样验证实际收益？

[[complexity-trap-summary|The Complexity Trap]]直接比较解题表现与成本：在受测软件工程任务中，摘要没有持续优于旧工具结果屏蔽，部分配置虽然省钱，解题率却下降。因此应加入简单方案作为对照，并让 Agent 真正继续执行。

下面是综合三篇材料的验证流程，不是某篇原文的统一评测标准：

1. **固定起点。** 选择有代表性的任务与历史快照，覆盖长工具结果、多次失败、用户纠正和多次压缩。保存环境状态与可核验答案。
2. **设置对照。** 从相同起点比较完整历史、旧工具结果屏蔽与摘要压缩；固定续跑模型、工具、任务限额及可回查资料。完整历史放不下时记录超限，不能偷偷裁剪后仍称其为完整历史。
3. **分别探测和续跑。** 一份副本做信息探针，另一份直接继续任务，避免探针及其答案影响后续行为。以测试或明确验收条件判定任务完成。
4. **统计并归因。** 汇总成功率、遗漏、补读、重复调用和总开销；计入摘要生成、缓存计费及后续额外轮次。多次运行观察波动，检查失败日志，避免凭单个案例或微小分差判定胜负。

评估一次压缩造成的信息损失时，应固定压缩点；比较整套管理策略时，则允许各自按规则触发，但保持任务和资源限制一致。最终按业务可接受的质量损失、成本与延迟选择方案；这些材料没有提供通用的合格压缩率。
