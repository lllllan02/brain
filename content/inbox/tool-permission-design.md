**可识别的工具行为用共享规则判断；无法可靠识别的调用，按策略审批、拒绝或受限执行。** 以下是结合参考资料形成的设计方案。

## 统一规则判断什么？

本地工具和 MCP 工具将可识别的行为转换成「主体、动作、资源、调用条件」，身份与资源归属来自可信上下文或业务系统。共享规则检查三件事：

- 主体能否执行该动作。
- 资源是否在授权范围内。
- 参数是否满足金额、环境等限制。

例如，多个订单查询工具都映射为 `order.read`，复用角色与资源范围检查。集中策略参考[[aws-agentcore-authorization-summary|AWS AgentCore]]，授权关系与动态条件参考[[openfga-agent-authorization-summary|OpenFGA]]。

## 哪些调用进入审批？

**审批分支也由规则明确规定，权限不足不自动意味着可以申请。** 规则仍匹配主体、动作、资源与条件，返回以下结果：

| 情况 | 处理 |
| --- | --- |
| 明确禁止且不允许例外，或没有允许、可申请依据 | 拒绝 |
| 当前权限不足，但具备申请资格，且有权批准的人可授予所需权限 | 申请额外授权 |
| 有业务权限，但缺少本次执行授权，或规则要求逐次确认 | 请求操作确认 |
| 权限与执行授权均覆盖调用，且无额外确认要求 | 直接执行 |

例如，假设退款规则允许客服自动处理 100 元以内退款，100～1000 元需主管批准，超过 1000 元拒绝。另一类规则可以要求「有发布权限，但 Agent 每次生产发布仍须确认」。业务权限决定用户能做什么，执行授权决定 Agent 能自主做到哪一步。

审批规则应写明「谁对什么操作、在什么条件下可以申请或必须确认，由谁批准、批准覆盖什么范围」。普通确认不能绕过禁止项；没有逐次确认要求且已有授权覆盖时，不必重复询问。

[[permit-agent-approvals-summary|Permit]]分别提供工具级审批和访问权限申请的参考；表中的分支是据此归纳的设计方案，具体条件由业务制度与用户委托决定。

## 复杂调用怎么处理？

Shell 可能通过变量、脚本和子进程产生额外行为，命令匹配无法完整推断副作用。判断依据是「本次行为能否可靠识别」，不是参数多少或工具名称。

- 能识别：检查动作、目标和关键参数；复合命令逐项检查，不能只看开头。
- 不能可靠识别：转审批或拒绝；已有受限执行授权时，也可由[[sandbox-execution|沙箱]]约束实际访问。未识别出危险，不等于可以无限制放行。

审批需展示实际命令、关键参数和申请范围，但人工批准也不证明脚本安全。具体机制参考[[claude-code-shell-permissions-summary|Claude Code 的解析与审查]]、[[codex-exec-policy-summary|Codex 的规则与沙箱决策]]。

## 执行链路

提取调用信息 → 求值规则 → 执行、拒绝或暂停申请。缺少允许依据、必要信息或检查失败时不直接放行；获批后核验当前调用仍在批准范围，再通过[[agent-human-in-the-loop|暂停与恢复机制]]继续。

规则可先用 Go 共享逻辑与配置实现，需要独立维护复杂条件时再引入策略引擎。
