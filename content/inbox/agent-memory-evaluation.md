**评估记忆要观察一系列交互之后，后续任务是否更正确、更省成本，并且能及时接受纠正。** 数据库里有记录和检索命中，都不能单独证明效果。

## 最小回归怎样构造？

沿用同一个假设用户与项目，按顺序执行：

| 历史或状态变化 | 后续检查 | 常见故障 |
| --- | --- | --- |
| 会话 A 明确 demo 项目偏好 Go | 新会话写示例 | 未保存、未触发读取或漏注入 |
| 会话 B 明确改成 Python | 再开会话，不带旧聊天 | 仍使用旧事实、索引未更新 |
| 另一个项目没有设置 | 查询那个项目 | 把局部偏好推广为全局 |
| 信息已过期或用户已删除 | 查询并运行后台整合后再查询 | 缓存残留、从旧摘要重新生成 |
| 当前请求明确“这次用 Rust” | 生成本次示例 | 历史默认覆盖当前要求 |
| 问及从未提供的事实 | 给出答案或请求补充 | 模型臆造“记得”某事 |

前三类同时测写入与使用；不能只预填一组正确记忆，再声称验证了自动提取。

## 怎样定位问题在哪一段？

在 [[agent-trace|Trace]] 中关联来源消息、候选、写入结果、记忆 ID／版本、召回候选、最终注入项与回答。然后分层判断：

- 应记而未形成候选：提取范围或触发策略问题。
- 候选正确却未入库：校验、写入或后台任务问题。
- 已入库却未召回：查询、过滤或索引问题。
- 已召回却未注入：去重、预算或当前版本核对问题。
- 已注入却答错：表达不完整、冲突未澄清或模型使用问题。

日志记录以必要证据为限，避免为了调试另存一份不受删除控制的敏感记忆。

## 怎样比较方案？

[[longmemeval-memory|LongMemEval 与 V2]]分别提供多会话事实记忆和环境经验的评测思路。它们能补充测试范围，但自己的业务还要测工具执行、删除、权限和故障恢复。

固定初始记忆快照、历史输入、模型、任务及输入预算，至少比较无跨会话记忆、简单文件或档案基线、候选方案；额外加入“直接提供正确证据”帮助判断读取瓶颈。各组使用隔离存储，避免前一次测试写入影响下一次。

同时记录任务成功率、纠正后旧事实误用、信息不足时的拒答，以及写入／查询延迟、输入 Token 和模型调用成本。Token 变少但成功率下降不算单独成立的收益；后台成本也必须计入。本文给出评测设计，尚未进行产品间同条件跑分。
