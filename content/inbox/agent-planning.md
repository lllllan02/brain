**ReAct 与 Plan-and-Execute 描述怎样组织推理、规划和行动；Replanning 描述执行过程中怎样调整计划。** 可以把它们放在「Agent 的规划与执行模式」下理解，但三者不是互斥的三种 Agent。

Planning（任务规划）是根据目标拆解任务、安排步骤的能力。[[agent-loop|Agent Loop]] 提供执行与反馈循环；在这个循环中，既可以逐步判断下一步，也可以先形成计划再执行。是否显式规划、何时回看计划，需要由程序规则或模型决策确定，不能仅凭任务复杂就假定系统会自动切换模式。

## 这些概念分别解决什么问题？

| 概念 | 关注的问题 | 主要特点与代价 |
| --- | --- | --- |
| [[react-agent\|ReAct（推理与行动交替）]] | 根据当前信息，接下来做什么？ | 能及时利用反馈；多轮判断增加开销，也可能反复尝试 |
| [[plan-and-execute\|Plan-and-Execute（先规划再执行）]] | 整体要完成哪些步骤，每一步怎样落实？ | 显式拆解目标，分开规划与执行；初始计划可能不适用，需要额外检查 |
| Replanning（重新规划） | 原计划哪些部分需要改变？ | 根据新证据调整剩余工作；频繁重规划也会增加成本、打断执行 |

ReAct 也能形成和修改计划；Plan-and-Execute 的执行器也能用 ReAct 完成单个步骤。**「分阶段规划」与「依据反馈调整」可以同时存在。**

## 计划什么时候需要改变？

[[agent-replanning|Replanning（重新规划）]]根据执行反馈或新要求调整剩余步骤。程序可在每个计划步骤后、固定行动间隔或指定事件发生时进入检查，再依据结果决定继续、重试、改计划或结束；检查不等于每次都改计划。

例如，排查性能时发现数据库正常、应用 CPU 异常，就需要检查原先「分析慢查询 → 检查索引」的后续计划是否仍适用。具体检查信号、模型与程序分工、状态更新和停止条件由重新规划卡片展开。

## 如何取舍，后续探索什么？

下一步高度依赖刚获得的信息时，可以先采用逐步交互；任务已有可识别的阶段、容易遗漏整体目标时，可以考虑显式规划。两者都不能保证成功，应比较任务完成情况和总耗时、费用，不仅比较是否生成了计划。

后续值得继续核对的问题是：计划应该细化到子目标还是具体工具调用？怎样为不同任务定义完成条件与计划检查规则？如果主要开销来自工具等待，能否像[[llmcompiler-summary|按依赖调度的规划方案]]那样并行执行独立步骤？这些问题分别涉及计划粒度、反馈策略与执行调度，暂不在这里展开实现。
