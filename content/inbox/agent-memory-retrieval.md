**记忆读取要回答三个问题：何时查询、哪些记录适用、最终让模型看到多少。** 相似度检索只解决其中一部分。

## 谁决定何时读？

| 策略 | 收益 | 代价与边界 |
| --- | --- | --- |
| 启动时固定加载 | 稳定偏好和必要规则不依赖检索触发 | 每轮占空间，内容必须短且有明确适用范围 |
| 程序按任务触发查询 | 已知字段或明确业务事件容易控制 | 开发者要定义触发条件，任务中途可能出现新缺口 |
| 模型调用记忆工具 | 能根据执行中的新问题补查 | 模型可能不查、查错，增加工具往返 |

[[letta-memory|Letta 的常驻块与归档]]、[[claude-code-memory|Claude Code 的索引与主题文件]]都展示了分层读取。可采用“少量必要信息先加载，细节按需补查”，但这是一种组合策略，不是所有任务的固定最优方案。每轮无差别重查会增加成本；只在启动时查，又可能错过中途变化。

## 找相似内容之前，先限定范围

以“给 demo 项目写示例”为例，应用先从可信身份确定用户 alice 和项目 demo，再按 `example_language` 读取当前偏好。明确属性用精确查询已经足够，无需先向量化问题。

若任务是“上次类似超时怎么解决”，措辞可能不同，可用关键词与语义召回寻找经历，再按环境、时间和结果过滤；必须看“当时用了什么条件”，不能只提取修复动作。[[graphiti-memory|关系图]]适用于还需追踪实体关系与历史有效期的问题。

权限与租户范围应进入存储查询条件；不能先把其他用户的数据交给模型，再让它自行筛掉。namespace、标签或 user_id 只是组织字段，只有程序限制调用者可使用哪些值时才形成访问边界。

## 找到了，为什么仍可能答错？

可采用如下应用链路：

「授权范围内召回 → 回查当前版本 → 检查有效期与适用条件 → 去重和排序 → 按预算组装 → 记录实际注入项」。

若旧记录是 Go，新记录已改为 Python，即使旧向量更接近查询，也应先核对当前事实。排序不能代替纠正。当前请求若明确“这次用 Rust”，则应识别为本次要求，不能被历史默认偏好压过。

[[agent-context|上下文管理]]负责把选中的内容放进模型输入，同时保留来源、范围与不确定性。内容应作为背景数据解释，不能把检索到的第三方文本提升成高权限指令。[[context-budget|Token 预算]]按实际模型输入计数，返回 5 条并不保证足够短。

记录“召回 ID／版本”与“实际注入 ID／版本”的差别，才能在[[agent-memory-evaluation|质量评估]]时定位：是找不到、预算筛掉，还是模型读到后仍使用错误。
