复制提供数据副本，Sentinel 为非分片主从部署监控并协调主节点切换，Cluster 同时提供分片与分片级故障切换。它们提高可用性，但异步复制仍可能丢失已确认写入。

## 副本如何追赶主节点

首次同步或历史无法衔接时，需要全量同步数据，再补齐期间的变化；复制标识和偏移量匹配、且所需历史仍在 backlog 中时，可做部分重同步。副本有延迟，刚写主节点后立刻读副本可能看不到新值。

主节点回复成功时，写入未必已经到达将来被选中的副本。WAIT 可以要求一定数量副本确认收到写入，但不能把整套系统变成强一致存储，也不能替代所有副本的持久化保障。

## Sentinel 如何切换

Sentinel 检查主节点状态，区分单个观察者的主观下线与达到配置共识的客观下线；实际执行故障转移还需要选出执行者并满足多数授权条件。它选取副本提升为新主，调整其他副本并通知客户端。客户端必须能够发现新主，不能永远连固定地址。

## Cluster 如何分片

Cluster 通常按 `CRC16(key) % 16384` 把 key 映射到 16384 个槽，每个槽由某个主节点负责，副本用于故障恢复。客户端根据槽路由：MOVED 提示更新槽归属信息，ASK 用于迁移过程中的临时转发，需要对目标请求配合 ASKING，不能据此永久改写槽映射。扩容需要迁移槽和数据，增加节点本身不会立刻均匀分散负载。固定槽与 [[consistent-hashing|一致性哈希环]] 是不同的映射方式。

多 key 操作通常要求位于同一槽，可用 hash tag 明确共置，但大量数据共用同一标签会重新形成热点。Cluster 中的脚本和事务也不能绕过跨槽边界。

故障切换的安全边界见 [Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。对不能容忍重复或过期持有者的操作，应继续设计 [[distributed-locks|外部资源侧的约束]]。
