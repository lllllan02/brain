**错例回流要把失败轨迹转成「可重新执行的输入、受控环境和独立验收条件」，再用新运行验证改动。** 保存 Trace 只保留了观察材料，尚未提供正确答案或完整测试环境。

## 先确定失败发生在哪个边界

假设用户查订单 A，回答却引用订单 B，沿「模型实际输入 → 调用参数 → 工具返回 → 下一轮实际输入 → 最终回答」核对：

- 参数已是 B：检查输入歧义、工具说明和模型选择。
- 参数是 A，返回 B：检查工具实现与数据。
- 返回 A，摘要却丢失订单号：检查上下文处理。
- 输入与结果都正确，回答仍为 B：检查生成与结果验证。

这是定位候选原因的顺序，不是单凭相关性证明根因。记录事实与待验证假设，并通过改变一个环节观察结果。按 [[anthropic-agent-evals-summary|Agent 评测方法]]，还要排除评分器误判与基础设施故障。

## 从哪个层次生成用例？

[[langfuse-dataset-experiments|Langfuse 的数据集与实验流程]]允许从整条任务或具体步骤建立数据项，并关联来源。选取层次时先明确要检验什么：

| 用例范围 | 固定哪些条件 | 能验证什么 |
| --- | --- | --- |
| 上下文变换 | 原始工具结果、变换规则与关键字段 | 新摘要是否仍丢订单号 |
| 单次模型调用 | 当轮实际消息、工具定义与模型参数 | 相同证据下参数或回答是否改善 |
| 完整 Agent 任务 | 用户输入、初始状态、工具数据与执行边界 | 新路径最终是否完成任务 |

每个用例保存输入、环境或固定数据版本、预期结果或检查规则、来源 Trace，以及被测代码和 Prompt 版本。对于查订单，应验证返回订单 A 的事实；不要把旧失败回答写成标准答案，也不要把一种合法工具顺序硬编码为唯一成功路径。

## 「重放」具体执行什么？

仅查看旧记录不会重新调用模型。固定工具返回值的测试会重新执行选定逻辑；从检查点重跑则可能重新访问真实服务。[[langgraph-time-travel|LangGraph 的时间旅行]]明确重新执行检查点之后的节点，包括模型、API 和人工中断，因此结果可能不同。

对写操作使用隔离环境或模拟工具，并核对实际副作用；检查点不能撤销已发送的邮件或已经提交的订单。模拟工具按名称、规范化参数与必要状态匹配返回值，不能只按「第几次调用」投喂旧结果，否则新路径可能错误消费旧数据。匹配失败应显式报出，不能默默回退真实写接口。

## 改动是否有效？

在同一数据集和评分规则上比较新旧版本：先看任务通过情况，再看用量、耗时与工具调用次数。保留每次实验的新 Trace，回看退化案例；模型具有随机性时应重复运行并报告次数，不能用一次通过证明稳定。

错例用来检验已知缺陷，还需保留正常与边界案例，检查修复有没有破坏原有能力。将调试中反复使用的样例与独立验证样例分开；有限且偏向失败的数据集不能直接代表线上成功率。
