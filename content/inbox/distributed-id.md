需要紧凑、趋势有序并在本地高吞吐生成 ID 时，可以组合时间戳、节点编号和窗口内序列号。唯一性依赖节点编号不冲突、时间窗口不被错误复用、序列号不溢出；这些是正确性前提。

## 从需求选择结构

若只要求低碰撞概率的独立生成，UUID 已可能足够。随机 UUIDv4 较长且不按时间排序；UUIDv7 则包含时间信息，不能把「所有 UUID 都随机无序」作为选择 Snowflake 的前提。[UUID 标准](https://www.rfc-editor.org/rfc/rfc9562.html)

更紧凑的整数 ID 可以按以下思路组织：时间戳提供趋势顺序，本地 sequence 区分同一时间窗口内的请求，workerId 区分不同生成实例。位数要在使用年限、并发节点数和单节点窗口吞吐之间分配，不能只背固定布局。

常见 Snowflake 示例把 64 位拆为 1 位保留位、41 位毫秒时间差、10 位节点号和 12 位序列。对应约 69.7 年时间范围、1024 个节点编号、每节点每毫秒 4096 个序列值；这些是编码容量，不是实际服务吞吐。跨语言传输时还要避免 JavaScript Number 超出精确整数范围，可使用十进制字符串或支持的大整数类型。

本地 sequence 更新必须同步；窗口内序列耗尽时等待下一窗口或拒绝生成，不能直接回绕。多个节点时钟不同，趋势有序也不等于全局严格递增。

## 节点编号怎样复用

可由[[etcd|etcd]]、[[zookeeper|ZooKeeper]] 或已有可靠协调能力分配 workerId，正常生成不访问远端。但租约到期只表示协调端允许重新分配，不保证旧进程已经停止。

旧实例长暂停后恢复、新实例已拿到同一编号时，可能产生冲突。必须设计租约失效后停发、重新取得资格，以及重启后历史时间窗口的保护。仅声称「用了心跳」不够；fencing token 也只有被编码进标识或由接收端验证时才有意义，不能凭空阻止本地产生重复 ID。

## 时钟回拨怎样处理

记录上次生成时间，发现当前时间更早时，小幅回拨可等待，超出容忍范围则停止生成或采用经过验证的逻辑时间策略。进程重启、workerId 重用和时钟回拨要一起检查，避免用同一编号重新进入曾经使用过的时间窗口。

若不想承担本地时钟和租约管理，也可评估数据库号段等方案；它把协调开销摊到一批 ID 上，但增加号段管理、空洞及服务可用性成本。
