title: "不同数据库应该怎样按访问模式选择？"

数据库选型先看数据如何写入、查询和更新，再看一致性、容量与延迟要求。按“结构化或非结构化”简单分类，无法判断事务、全文检索和大范围聚合的差别。

| 主要需求 | 适合评估的模型 | 代表与边界 |
| --- | --- | --- |
| 多实体约束、事务和关联查询 | 关系模型 | MySQL 等；需要索引与事务设计 |
| 按 key 低延迟访问 | 键值模型 | [[redis\|Redis]]；关注内存、持久化与热点 |
| 以完整对象读写嵌套结构 | 文档模型 | [[mongodb\|MongoDB]]；结构灵活仍需建模 |
| 文本相关性和多条件检索 | 倒排索引 | [[elasticsearch\|Elasticsearch]]；关注分析器与可见延迟 |
| 大量明细上的过滤和聚合 | 列式分析 | [[clickhouse\|ClickHouse]]；排序与扫描范围关键 |
| 带标签的指标时间序列 | 时序模型 | [[prometheus\|Prometheus]]；控制标签基数 |
| 向量近邻召回 | 向量索引 | [[rag-retrieval\|RAG 检索]]；需评估召回率、过滤与更新成本 |
| 多跳关系遍历 | 图模型 | 关系路径与访问模式决定收益 |
| 大对象与长期归档 | 对象存储 | 用于文件和归档，查询通常依靠额外元数据或计算层 |

例如订单交易用关系数据库维护状态与约束，搜索副本提供检索，分析库计算销量。这些副本可以由 [[cdc|CDC]] 派生，但需要接受并管理传播延迟，不能让每个系统都各自成为同一业务事实的权威。

先用已有系统验证查询与容量，再决定是否引入新组件。新增一种存储，也会新增备份、恢复、监控、权限和跨系统一致性问题；功能匹配之外，这些成本同样影响选择。
