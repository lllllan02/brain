消息队列把生产与消费解耦，但可靠投递、重复处理、消费顺序和积压容量是独立问题，不能用“消息已经入队”一起回答。

异步化适用于不必在返回前完成的工作，队列用等待时间换取短时削峰，并不增加下游长期处理能力。业务数据与待发送事件可在同一数据库事务中写入 Outbox，再由后台投递；独立执行「提交业务，再发送消息」仍存在丢失窗口。

对于分区日志型队列，消息进入分区后通常追加到日志，按段存储，以便顺序写入和批量读取。分区决定并行度与局部顺序；副本决定节点故障时的数据可用性。生产确认发生在写入侧，消费确认发生在业务处理侧，两者不能互相替代。

| 问题 | 需要明确的约束 |
| --- | --- |
| 生产端何时收到成功 | 已写入哪个介质、多少副本；超时后如何判定和重试 |
| 消费进度如何记录 | 按消息确认还是按分区位点；处理与确认之间是否有事务边界 |
| 消费者失败后怎么办 | 重新投递、退避重试、隔离毒消息及人工恢复流程 |
| 怎样保序 | 同一业务键路由到同一分区，分区内处理也不能随意并发 |
| 积压多久可承受 | [[queue-backlog-capacity\|吞吐差额、保留时间与存储容量]] |

至少一次投递通常意味着消费端可能重复执行。扣款、发券等业务需要[[idempotency|唯一业务键和持久化去重]]，把去重记录与业务变更放在同一事务中；内存里记录“见过这个消息”不能跨进程故障保证正确性。

选择 [[message-delivery-push-pull|推送或拉取]] 会影响流控方式；选择 [[kafka|Kafka]] 这类可重放日志，则还需要独立设计消费组、保留策略和位点恢复。重试队列、延迟队列与死信队列不是所有产品都具有相同语义，设计时应核对实际实现。

## 产品模型怎样影响选择

Kafka 的分区日志适合独立消费进度与重放；RabbitMQ 用 Exchange、Binding 和 Queue 表达路由，且需要区分普通队列、仲裁队列与 Stream。不能把「RabbitMQ 消费完即删除、不支持重放」写成覆盖所有类型的结论。[Exchange](https://www.rabbitmq.com/docs/exchanges)、[Streams](https://www.rabbitmq.com/docs/streams)

RocketMQ 的事务消息通过半消息、提交或回滚以及事务回查，协调本地事务结果与消息可见性；它没有把消费者的数据库操作自动加入生产者事务，消费者仍需幂等与恢复。[事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)

比较产品时固定消息大小、确认与持久化条件、副本数、积压量和延迟目标，再验证路由、顺序、延迟投递与故障恢复。原资料中「日志选 Kafka、交易选 RocketMQ」只可作为初步场景线索，不能替代这些约束。
