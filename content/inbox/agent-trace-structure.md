**在 Harness 的运行、模型请求与工具执行边界创建 Span，并把追踪上下文传给实际执行者，才能让并行、重试和跨服务调用保持正确归属。** 只在日志里打印相同任务 ID，仍不足以还原步骤之间的包含关系。

## 埋在哪里？

一次查订单任务可按「运行 → 模型选工具 → 查询订单 → 模型生成回答 → 验收」记录。两个模型调用和工具执行都属于运行；工具由模型提出，不代表它在模型请求尚未结束时执行，因此不应仅凭这种逻辑关联把工具挂在已结束的模型 Span 下。

[[langfuse-tracing|Langfuse 的粒度建议]]要求每次模型调用单独可见。已有 SDK 集成时，复用其模型与工具埋点，再补应用层的运行、审批和验收；手工包装同一调用前先检查自动埋点，避免生成两份相同操作记录。Go 项目接入可参考[[eino-langfuse-tracing|Eino 的 Langfuse 集成]]，先核对扩展提供的回调与导出能力。

| 标识或关系 | 表达什么 | 不能替代什么 |
| --- | --- | --- |
| Trace ID、Span ID、父 Span | 本次运行与操作归属 | 不表示工具参数或消息对应关系 |
| Tool call ID | 模型提议与工具结果的配对 | 不等于一次实际尝试的唯一标识 |
| 尝试序号或 Attempt ID | 同一逻辑调用的各次重试 | 不覆盖前一次失败 |
| Task ID、Session ID | 跨运行的任务或会话 | 不应强迫所有运行共享一个根 Span |

## 并行与重试怎样记录？

并行查询订单和物流时，两个工具从同一个运行上下文创建兄弟 Span，各自记录开始结束时间。查询订单超时后重试，则给两次尝试分别记录 Span，用同一逻辑调用标识关联，并保留尝试序号。重试成功只改变最终运行结果，先前超时仍是有效证据。

按 [[otel-trace-collection|OTel 的 Context 传播方式]]，Go 中应把 `tracer.Start` 返回的 Context 继续传入下游；启动 goroutine 时显式传入合适的父 Context。跨服务则在请求或消息载体中注入上下文，由接收方提取后创建 Span。这里的 Context 是追踪关联信息，与模型上下文是两类对象。

等待人工数小时后另起运行时，可保留 Task ID，并按需要用 Span Link 关联前次操作；Span Link 是关联关系，不把两条 Trace 合并成一棵父子树。实际传播和链接由 SDK 完成，不手工复用 Span ID。

## 怎样判断采集结果可信？

检查一次成功、一次工具失败、一次并行调用：应能看到各次模型请求、工具结果配对、独立尝试和停止原因。不能用父 Span 耗时加子 Span 耗时计算任务总时长；并行步骤耗时也不能直接相加。

操作失败时同时核对错误事件与 Span 状态，例如 Go 的 `RecordError` 不自动设置 Error。业务验收另记结果：HTTP 成功、Span 未报错，都可能伴随错误答案。步骤存在但后台看不到时，再检查[[opentelemetry-collector|采样、导出队列与关闭时的刷新]]；这与漏埋点需要分别排查。
