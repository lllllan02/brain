网络文件系统把本地文件 API 转换为远程请求。缓存减少网络访问，却需要明确其他客户端何时看见更新；协议维护的状态越多，重启后的恢复协调通常越复杂。

以下比较限定于 OSTEP 讨论的 NFSv2 与经典 AFS 设计，不代表所有现代 NFS、AFS 实现。

## NFSv2 为什么让请求自带操作位置

NFSv2 的 READ、WRITE 携带文件句柄、偏移和长度，服务器无需维护每个客户端的打开偏移。句柄可包含文件系统、inode 与生成号，避免旧句柄误指向复用后的 inode。

响应丢失时客户端重试。向同一偏移写入同样内容有利于重复执行，但并发写入介入后，旧请求重试仍可能覆盖新值；创建、删除等操作也不能仅凭「无状态」就获得端到端恰好一次保证。请求效果与重试边界见 [[idempotency|幂等性]]。

教材中的 NFSv2 稳定写要求服务器持久化后确认。不能将其推广为所有版本的每种 WRITE；不同协议版本对不稳定写入与提交有各自规则。

## 缓存何时失效

NFS 客户端可通过属性验证缓存，并在关闭与再次打开之间协调刷新与检查。属性缓存减少请求，也留下暂时读取旧数据的窗口，不能当成跨客户端的即时共享内存。

经典 AFS 以整文件本地缓存和关闭时写回减少远程 I/O，用 callback 让服务器在更新时通知持有缓存的客户端失效。整文件缓存有利于重复读取，小范围访问大文件却可能搬运多余数据；并发修改时的最后关闭者覆盖也不等于合并双方修改。

## 回调状态丢失以后怎么办

客户端或服务器重启可能丢失 callback 状态，必须重新验证缓存和建立承诺。收不到失效通知不能被解释为缓存永远有效。缓存策略同时决定正常路径开销与故障后的恢复步骤。
